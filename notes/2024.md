**Ontology-Guided Knowledge Graph Creation**

* This approach contrasts with previous methods that relied on no-code tools, shifting the focus to programmatic control using Python.
* The process involves extracting structured information (entities, attributes, and relationships) from unstructured sources like web pages or text documents.

**Defining and Using Ontologies**
* An ontology can be defined using formal standards like *Turtle* or *OWL* (Web Ontology Language), which are machine-readable. Tools like *WebProtégé* are useful for editing and exporting these definitions.
* Ontologies define classes (types of nodes) and object properties (relationships), including specific 'domain' and 'range' constraints. These constraints specify the starting and ending points of relationships, preventing illogical connections (e.g., ensuring a 'was created by' relationship connects an artwork to an artist, not vice versa).
* Even if formal ontology editors are not available, simple natural language descriptions of the domain schema can be passed to an LLM, which is often sufficient to guide the output effectively.

**Technical Implementation**
* The process utilizes libraries like *RDFLib* to parse and serialize ontology files, which are then passed as context to an LLM (such as *GPT-4o*) alongside the raw source text.
* The LLM is instructed via system prompts to generate *Cypher* queries that respect the provided ontology's structure, labels, and properties.
* The code iterates through data sources, using the *MERGE* command in *Cypher* to populate the *Neo4j* database, which helps in avoiding duplicate nodes when the same entity appears in multiple documents.

**Challenges and Future Considerations**
* **Entity Resolution and Duplication:** A persistent challenge is the lack of globally unique identifiers. If the LLM generates slightly different names for the same entity across different processing passes, they will not automatically merge in the database. Addressing this is a priority for future episodes.
* **Scaling Ontologies:** Passing an entire, large-scale ontology in every LLM request becomes inefficient as the vocabulary grows. Future approaches may require fine-tuning models to 'internalize' the ontology knowledge rather than passing it in the prompt context.
* **Data Quality and Validation:** The video emphasizes that LLMs can sometimes be unpredictable. *SHACL* (Shapes Constraint Language) shapes serve as a vital mechanism for post-generation validation, allowing developers to define formal patterns that, if violated, can be identified, flagged, or automatically corrected within the database.
* **Human-in-the-loop:** The database provides full control, meaning that if errors occur (such as incorrect relationship directions), one can either automate corrections or curate the data manually.

### 3. Main goal of this episode

The central idea was to demonstrate how the **GraphRAG Python package** can be used for:

1. Knowledge Graph construction.

3. Entity resolution/deduplication.

### 4. GraphRAG Python package

The package was presented as having three major areas:

* **Knowledge Graph Builder** — constructs the graph from source data.
* **RAG/retrieval** — retrieves information and generates answers.
* **Pipelines** — combine multiple processing steps into an end-to-end workflow.

The package supports several retrieval strategies, including:

* Vector retrieval.
* Vector + graph/Cypher approaches.
* Custom retrievers.
* Text-to-Cypher retrieval.

### 5. Ontology is useful but not strictly required

* An ontology is **not mandatory** for using the GraphRAG package.
* You can perform entity extraction without a formal ontology.
* However, some kind of schema/semantic definition is still needed to tell the system what entities, properties, and relationships it should look for.
* A formal ontology provides a standardized and reusable way of expressing this information.

The speakers emphasized that an ontology does **not have to be huge**:

* It can be very small and specific to an application.
* It can grow incrementally.
* Existing ontologies and vocabularies should be reused rather than recreated.

Examples mentioned:

* `schema.org`
* Enterprise/domain-specific ontologies.
* Getty's **Art & Architecture Thesaurus (AAT)**.

### 6. The example dataset

The demonstration reused the **Tate Modern artwork dataset** from previous episodes.

The data consisted primarily of unstructured text describing:

* Artists.
* Artworks.
* Artwork descriptions and related information.

The goal was to turn this unstructured information into a Knowledge Graph.

### 7. Ontology used in the demonstration

The example ontology defined two main classes:

* **Artist**

  * Defined as a subclass of `Person`.
* **Artwork**

  * Defined as a subclass of `CreativeWork`.

It also defined properties such as:

* Artwork title/name.
* Artist professional name.

And relationships such as:

* An artwork **was created by** an artist.
* An artwork **represents** a person.
* Other relationships such as influence.

The ontology was represented using **RDF**, created with a visual ontology editor, and read in Python using `rdflib`.

### 8. Knowledge Graph construction pipeline

The pipeline consisted of several components:

* Connection to a Neo4j database.
* Ontology/schema.
* Text splitter.
* Embedding service.
* LLM for entity extraction.
* Knowledge Graph Builder.

For the demonstration:

* Text was split into chunks of approximately **2,500 characters**.
* A small OpenAI embedding model was used to create embeddings.
* GPT-4o was used for entity extraction.
* The extracted entities and relationships were stored in Neo4j.

### 9. Two-layer graph architecture

The resulting graph had two conceptual layers:

**Lexical graph**

* Represents chunks of the original unstructured documents.
* Chunks contain embeddings.
* Enables vector-based retrieval.

**Domain graph**

* Contains extracted entities such as artists and artworks.
* Contains relationships between those entities.
* Represents the semantic/domain structure of the source data.

This allows the same source data to support both **vector RAG and graph-based retrieval**.

### 10. Entity extraction

The ontology was used to guide entity extraction.

Instead of simply asking the LLM to find arbitrary entities, the schema tells it what the graph should contain:

* Which entity types exist.
* Which properties they have.
* Which relationships can exist.

This helps ensure that the generated Knowledge Graph conforms to the intended model.

### 11. Entity resolution / deduplication problem

An important problem appeared after extraction: **duplicate entities**.

For example, the graph contained multiple nodes representing:

* David Hockney.
* Other artists with variations in their names.
* Repeated artworks.

The problem occurs because different pieces of text can refer to the same real-world entity using slightly different representations.

### 12. Basic entity resolution

The GraphRAG package has a basic entity-resolution mechanism.

By default, it can identify entities when they have:

* The same label/type.
* The same name.

However, the demonstration used custom properties such as `professionalName` instead of the standard `name` property, so additional configuration was required.

### 13. Ontology-driven primary keys

The solution was to mark certain ontology properties as **inverse functional properties**.

In practical terms, these behave like **primary keys** for entity resolution.

For example:

* If two Artist nodes have the same professional name, they should represent the same artist.
* If two Artwork nodes have the same title identifier, they should represent the same artwork.

The pipeline:

1. Reads the ontology.
2. Finds inverse functional properties.
3. Treats those properties as entity-resolution keys.
4. Creates appropriate resolvers automatically.

This allowed multiple David Hockney nodes to be merged into one.

### 14. Entity resolution is still an unsolved/advanced problem

The basic exact-match approach isn't enough for cases such as:

* “Hockney”
* “David Hockney”

The speakers discussed several possible approaches:

* String similarity.
* Levenshtein distance.
* Jaro-Winkler.
* BM25.
* Semantic similarity.
* Embedding-based matching.
* Structural similarity.
* Graph neighborhood similarity.
* External/master reference data.
* Custom entity-resolution logic.

They specifically mentioned that **Neo4j Graph Data Science** could potentially help by comparing the neighborhoods of nodes. If two apparently different artists are connected to many of the same artworks, that structural similarity can provide evidence that they are actually the same entity.

### 15. Master/reference data

Another proposed approach is to use a trusted reference dataset.

For the artwork example, the Tate Modern catalog could act as a **master source of artists**.

That reference data could help resolve ambiguous or inconsistent names.

The speakers noted that more sophisticated entity resolution would be explored in future episodes.

### 16. Vector RAG

Once the graph has been constructed, it can be queried using RAG.

The first demonstrated approach was **vector retrieval**:

1. User asks a question.
2. The question is converted into an embedding.
3. Vector search finds relevant text chunks.
4. The retrieved chunks are passed to the LLM.
5. The LLM generates the answer.

Example:

* Question: Who painted *La Femme...*?
* Vector retrieval finds the relevant artwork description.
* The system returns **Pablo Picasso**.

### 17. Limitation of pure vector search

The speakers pointed out that vector search can struggle when the answer is:

* Spread across multiple chunks.
* Dependent on relationships between entities.
* Requiring multiple retrieval/ranking steps.

This is where **graph-based retrieval** can complement vector retrieval.

### 18. Text-to-Cypher

The second RAG approach demonstrated was **text-to-Cypher**.

Instead of searching text chunks:

1. The user asks a natural-language question.
2. The system receives the graph schema.
3. An LLM generates a Cypher query.
4. The query is executed against Neo4j.
5. The result is returned as the answer.

Example:

* Question: Who painted *The Master Printer of Los Angeles*?
* The LLM generated a Cypher query connecting:

  * Artwork
  * `wasCreatedBy`
  * Artist
  * `professionalName`
* The result was **David Hockney**.

### 19. Ontology also drives text-to-Cypher

The ontology was used again to provide the schema to the LLM.

It tells the LLM:

* Which node labels exist.
* Which properties exist.
* Which relationships connect entities.

This prevents the LLM from having to guess the terminology used in the graph.

The ontology was converted into a more readable natural-language representation before being supplied to the LLM.

### 20. The same code can work for different domains

One of the major takeaways was that the demonstrated Python pipeline contains **little or no domain-specific logic**.

To apply it to another domain, you could:

1. Choose a different dataset.
2. Define an ontology for that domain.
3. Specify the relevant entities.
4. Specify their properties.
5. Specify their relationships.
6. Run essentially the same pipeline.

Examples mentioned include:

* Product catalogs.
* Literature.
* Other specialized datasets.

The ontology becomes the central configuration describing how the system should behave.

### 21. Three major places where the ontology is reused

The episode demonstrated the ontology influencing three stages:

**1. Entity extraction**

* Determines what entities and relationships should be extracted.

**2. Entity resolution**

* Defines properties that can act as identity/primary-key-like fields.

**3. RAG/text-to-Cypher**

* Provides the graph schema needed to generate queries.

This reuse was presented as the main reason for having a centralized semantic definition.

A question asked why RDF was used instead of Pydantic models.

Formats mentioned include:

* RDF/XML.

### 28. Overall architecture demonstrated

The whole workflow can be summarized as:

**Unstructured data → chunking → embeddings + entity extraction → Knowledge Graph → entity resolution → retrieval/RAG → answer**

And the ontology influences the pipeline at multiple stages:

**Ontology → entity extraction**
**Ontology → entity resolution**
**Ontology → text-to-Cypher/RAG**

### 29. Final takeaway

The main message of the episode was that **GraphRAG is more versatile than simply “RAG over a graph.”**

It can provide an end-to-end pipeline for:

* Building a Knowledge Graph.
* Extracting structured entities from unstructured data.
* Resolving duplicate entities.
* Creating vector indexes.
* Performing vector retrieval.
* Generating Cypher from natural language.
* Using an ontology as a centralized semantic specification across these stages.

The strongest conceptual takeaway is: **define the domain once through a reusable ontology, then let that definition drive multiple parts of the Knowledge Graph/RAG pipeline.**
