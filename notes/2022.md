# Broadcast 1: Feb 1

Here are the main points made in the transcript, organized by topic:

### 1. Purpose of the series

* The session launches a new monthly series called **“Going Meta – A Series on Graph, Semantics and Knowledge.”**
* The series is aimed primarily at **practitioners** who build and work with data systems.
* The goal is to make topics such as **semantics, ontologies, RDF, interoperability, and knowledge graphs** practical rather than purely theoretical.
* Sessions will emphasize **hands-on demonstrations, live coding, examples, and real datasets**.
* Attendees are encouraged to suggest topics for future sessions.

### 2. Why discuss semantics and ontologies?

* Terms such as **knowledge graph, semantics, ontology, and interoperability** are frequently used but can be ambiguous.
* Online explanations are often high-level and don't clearly explain what these concepts mean when actually working with data.
* The presenters want to demonstrate what these concepts **look like in practice**.
* A recurring theme is that semantics involves representing **things and relationships between things**, naturally leading to graph-based representations.

### 3. Jesús Barrasa's background

* Jesús Barrasa is presented as a **Neo4j expert in semantics, ontologies, and RDF**.
* He has experience on both sides of the graph ecosystem:

  * Academic work/PhD in **Knowledge Representation**.
  * Experience with **RDF and ontologies**.
  * Work modeling telecommunications/network-management data using RDF.
  * Several years working with **Neo4j and property graphs**.
* He has experience with both **SPARQL** and **Cypher**.
* This background makes him well positioned to compare RDF and property graphs.

### 4. Main topic of the session: RDF vs. property graphs

The session compares two approaches to representing and querying graph data:

* **Property graphs**, using Neo4j and Cypher.
* **RDF graphs**, using a triplestore and SPARQL.

The presenters emphasize that the goal isn't to declare one universally better, but to show **how the two approaches differ in practice**.

### 5. The example dataset

* They use the **British Library Catalogue** as a public dataset.
* The dataset exists in:

  * RDF/triplestore form at the British Library.
  * A property-graph representation imported into Neo4j.
* The Neo4j version contains roughly:

  * **20 million nodes**
  * **87 million relationships**
  * The original RDF import involved hundreds of millions of triples.
* They run equivalent queries against both representations.

### 6. Property graph model

The property graph is described as a relatively **high-level representation**.

Its fundamental building blocks are:

* **Nodes** — representing entities.
* **Relationships** — connecting entities.
* **Properties** — attributes belonging to nodes or relationships.

Example:

* A person is represented by a node.
* A company is represented by another node.
* A `WORKS_FOR` relationship connects them.
* The person can have properties such as name and date of birth.
* The relationship itself can have properties such as start date or role.

The presenters describe this as relatively close to how humans naturally think about entities and connections.

### 7. Cypher

* Neo4j uses **Cypher** to query property graphs.
* Cypher syntax visually resembles the graph structure.
* A query can essentially describe:
  **node → relationship → node**
* This makes graph traversal relatively direct and readable.
* The query language operates at the level of **entities, nodes, and relationships**.

### 8. RDF model

RDF is presented as a **lower-level representation**.

Its basic building block is the **triple**:

* Subject
* Predicate
* Object

For example:

* Person → has name → Jesús
* Person → has date of birth → date
* Person → works for → company

Rather than putting all properties directly on an entity, RDF represents information as individual statements/triples.

### 9. Why RDF can look more verbose

* RDF can appear much more verbose because each statement is represented separately.
* Values such as names or dates can themselves appear as nodes in the RDF graph.
* The graph therefore contains a more detailed decomposition of the information.
* The presenters characterize this as a **lower-level representation** compared with a property graph.

They compare this conceptually to:

* Higher-level programming code → lower-level compiled instructions.

The same information can be represented at different abstraction levels.

### 10. Why RDF was designed this way

* RDF originated in the context of the **Semantic Web**.
* One of its goals was to represent information that could be **distributed across different websites and datasets**.
* Information could be broken into small, independently usable statements.
* RDF's use of globally identifiable resources makes it possible to combine information from different sources.

### 11. URIs and vocabularies

A major RDF concept discussed is that resources are identified using **URIs**.

Instead of simply saying something is a `Book`, RDF can identify the precise vocabulary definition, such as a definition from **schema.org**.

They demonstrate the use of prefixes such as:

* `schema.org`
* `dct`
* `FOAF`
* ISBN-related namespaces

Prefixes make otherwise long URIs easier to read.

### 12. Interoperability

* RDF's use of globally identified concepts and standard vocabularies can facilitate **interoperability**.
* Different datasets can refer to the same or related concepts using standardized identifiers.
* Different vocabularies can coexist.
* The presenters note that the relationship between RDF and property graphs is more nuanced than simply saying they're completely separate worlds.

### 13. Querying a book by ISBN

They demonstrate the same task in both systems:

> Find a book using its ISBN.

In Neo4j/Cypher:

* Find a node labeled as a book.
* Look at its `ISBN 13` property.
* Return the book node.

In SPARQL:

* Define the relevant namespaces.
* Match triples saying something is a book.
* Match the ISBN triple.
* Retrieve information about that book.

Both approaches return the same underlying information.

### 14. Querying books by author

They next ask:

> What books were written by Ian Rankin?

In Cypher:

* Find a person named Ian Rankin.
* Traverse the `creator` relationship to books.
* Return book titles.
* Optionally order the results.

In SPARQL:

* Find a person of type `schema:Person`.
* Match their name.
* Follow the relevant `creator` predicate to books.
* Retrieve the titles.

Again, the **same information can be retrieved**, but the query expresses the traversal differently.

### 15. Direction of relationships

* Property-graph relationships have a **direction**.
* If the query assumes the wrong direction, it may return no results.
* Explicitly specifying the correct direction can also help the query engine narrow the search.
* RDF predicates similarly have a defined direction from subject to object.
* SPARQL provides mechanisms for traversing relationships in the opposite direction.

### 16. Duplicate results and `DISTINCT`

* Queries can sometimes produce duplicate results.
* Both Cypher and SPARQL provide mechanisms for eliminating duplicates.
* They demonstrate using `DISTINCT` to obtain a clean list.

### 17. Partial text searches

They demonstrate searching when the full author's name isn't known.

In Cypher:

* Functions such as `CONTAINS` and `STARTS WITH` can be used.
* Example: search for authors whose names contain `"Rankin"`.

In SPARQL:

* A **regular expression** can be used to perform partial matching.
* Regex is very powerful but can be more technical/verbose.
* The query can express patterns such as text beginning or ending with particular characters.

### 18. Searching by subject/category

They then search for books associated with the subject:

> **Crystallography**

In the graph:

* A concept/subject represents crystallography.
* Books have a relationship to the concept.
* The query traverses from the subject to books.
* Authors and titles can then be retrieved.

### 19. Aggregating books by author

They demonstrate a more sophisticated query:

* Find books about crystallography.
* Find their authors.
* Group the books by author.
* Return an author along with a comma-separated list of their books.

Cypher uses a collection operation such as `collect`.

SPARQL uses:

* `GROUP_CONCAT`
* A separator to combine multiple book titles into a string.

This illustrates that the same analytical operation is possible in both query languages, although the syntax differs.

### 20. Related concepts

A participant asks whether they could find concepts related to crystallography.

They demonstrate one simple definition of "related":

* Find concepts that occur together on the **same books**.
* For example, if books are tagged with both crystallography and electron microscopy, the two concepts can be considered related in the context of this dataset.
* They can count how many books connect two concepts.
* This provides a way to **expand a search** from one topic to related topics.

They mention that future sessions could explore more sophisticated graph algorithms for discovering relationships.

### 21. RDF vs. property graph: central conceptual distinction

The main conceptual distinction throughout the session is:

**Property graph**

* Entity-oriented
* Nodes + relationships + properties
* Higher-level abstraction
* Cypher directly expresses graph patterns

**RDF**

* Statement-oriented
* Subject + predicate + object triples
* More granular/lower-level representation
* SPARQL expresses patterns over triples

The presenters stress that **the same underlying information can be represented and queried using either approach**.

### 22. RDF is not necessarily tied to one storage technology

* RDF is primarily a **data model/exchange model**, not simply a particular database.
* RDF can be stored in:

  * A specialized triplestore.
  * A relational database.
  * Other systems that expose RDF representations.
* Therefore, questions about the best use case for RDF cannot be answered solely by looking at the RDF model; the underlying storage system and application requirements also matter.

### 23. Performance and storage differences

They discuss what happens underneath the query languages.

In a typical RDF/triplestore:

* Triples can be thought of as a large collection/table of subject-predicate-object records.
* Traversing several relationships can involve many **joins**.
* Query-time joins can become increasingly expensive as datasets grow.

In Neo4j:

* Relationships are stored as **first-class graph structures**.
* Relationships are persisted natively.
* Traversal can follow stored references/pointers between entities.
* This is presented as a key architectural difference affecting graph traversal performance.

### 24. Relationship properties

A question asks whether relationships can themselves store information.

In Neo4j:

* Relationships are first-class entities in the graph model.
* They can have their own properties.
* Example:

  * Person → works for → company
  * The `works for` relationship can contain a start date or role.

Historically, RDF handled this differently:

* Additional information about a relationship could require **reification/an intermediate node**.
* The presenters mention **RDF-Star** as an RDF extension that allows statements about statements, making this kind of relationship metadata easier to represent.

### 25. Choosing between RDF and property graphs

The presenters deliberately avoid giving a simple:

> “Use RDF for X and property graphs for Y.”

They emphasize that the answer depends on:

* The data model.
* Storage technology.
* Use case.
* Interoperability requirements.
* Query requirements.
* Skills available.
* Development and query-maintenance considerations.

They also point out that technology choices have consequences for **finding and maintaining developer expertise**.

### 26. Skills and ecosystem considerations

A project manager or product owner might need to consider:

* How easy it is to find people skilled in SPARQL.
* How easy it is to find people skilled in Cypher.
* How widely each technology is used.
* Community activity and available resources.

They suggest looking at sources such as Stack Overflow to understand the broader developer ecosystem.

### 27. Future sessions

Future sessions are expected to go deeper into:

* RDF.
* Knowledge graphs.
* Interoperability.
* More advanced graph queries.
* Related concepts.
* Potentially graph algorithms.
* Other practical aspects of working with these technologies.

### 28. Code and resources

* The presenters plan to **share the code** used during the session.

### 29. Overall takeaway

The central message of the session is essentially:

> **RDF and property graphs can represent the same underlying knowledge, but they do so at different abstraction levels and consequently require different ways of querying and working with the data.**

The session is primarily intended to **show those differences concretely**, rather than argue that one model universally replaces the other.

# Broadcast 2: Mar 1

Here are the main points made in the session, organized by topic:

### 1. What semantic search is

* Semantic search goes beyond traditional **keyword/text-based search**.
* Traditional search looks for exact terms appearing in documents.
* Keyword search can be limited by:

  * Ambiguity — e.g. “Boston” could mean the city or the music band.
  * Spelling differences — e.g. searching for “Neo4k” instead of “Neo4j.”
  * Synonyms and related concepts.
  * The need for the user to choose the “right” search terms.
* Semantic search aims to search for **things/concepts rather than strings of text**.

### 2. The two key ingredients of semantic search

The demonstration describes two major components:

**A. Understanding the documents**

* Start with unstructured documents containing natural-language text.
* Use NLP/entity-extraction tools to identify what the documents are about.
* Extract **entities**, rather than treating everything as simple keywords.
* For example:

  * “Boston” → the city/location Boston.
  * “Neo4j” → an organization.
  * “MongoDB” → a particular technology/entity.
* Tools/services that can perform this include NLTK, Hugging Face, spaCy, cloud NLP services, etc.
* In the demo, **Google Cloud entity extraction** was used through Neo4j/APOC.

**B. An organizing principle / ontology**

* Extracted entities need to be connected to knowledge about the domain.
* This knowledge can be represented as:

  * An ontology.
  * A taxonomy.
  * A concept scheme.
  * Other structured descriptions of how concepts relate.
* Example:

  * Boston → located in → United States.
  * MongoDB → type of → NoSQL database.
  * Redis → type of → key-value database → type of → NoSQL database.

### 3. What an ontology means here

* An ontology is essentially an **explicit description of a domain and the relationships between its concepts/entities**.
* It makes knowledge that might otherwise be implicit explicit in the graph.
* More sophisticated ontologies can specify properties such as transitivity or inverse relationships.
* Standards such as **OWL, SKOS and RDF/RDFS** can be used.
* You don't necessarily have to create an ontology from scratch; existing public ontologies can be reused.

### 4. Why entities are different from keywords

* A keyword is just a piece of text.
* An entity represents something with **meaning in a particular context**.
* Entity extraction can identify that a word/phrase refers to a specific real-world concept.
* A unique identifier can then be associated with that entity.
* This allows it to be connected to other knowledge in the graph.

### 5. The worked example

The demonstration builds a semantic search system in Neo4j.

The process was:

1. Load technology articles from a CSV file.
2. Create an `Article` node for each article.
3. Store article properties such as:

   * Title
   * Body
   * Date
   * URI/source
4. Import domain knowledge from **Wikidata**.
5. Represent that knowledge as a taxonomy/concept scheme.
6. Clean up redundant relationships in the taxonomy.
7. Run entity extraction against each article.
8. Match extracted entities to concepts in the ontology.
9. Connect articles to those concepts.
10. Use graph traversal to perform semantic search.

### 6. Wikidata as a source of domain knowledge

* Wikidata was used as an existing source of structured knowledge.
* It was described as a large collaborative knowledge base, somewhat like a structured version of Wikipedia.
* A relevant subset of Wikidata was extracted for the technology domain.
* It was represented using **SKOS/RDF**.
* The example contained concepts such as databases, programming languages, serialization formats, etc.
* Neo4j's **neosemantics** plugin was used to import this information.

### 7. Cleaning the ontology

* The imported taxonomy contained some redundant “shortcut” relationships.
* Example:

  * JSON-LD → JSON → data serialization format.
  * If JSON-LD is also directly connected to “data serialization format,” that direct relationship can be derived from the longer path.
* These redundant relationships were removed.
* About 500 such relationships were deleted in the demo.
* This was mainly graph housekeeping rather than an essential semantic-search step.

### 8. Connecting documents to the ontology

* The articles initially existed as isolated nodes containing text.
* Entity extraction was run over each article.
* Google Cloud's NLP service identified entities.
* Some extracted entities included a **Wikipedia URL/identifier**.
* The ontology had corresponding identifiers stored as alternative labels.
* These identifiers were used to connect extracted entities from articles to concepts already present in the graph.
* This effectively connected the **document layer** with the **domain-knowledge layer**.

### 9. The resulting graph

The resulting structure looks conceptually like:

**Article → Entity/Concept → Related Concept → Related Concept**

For example:

**Article → Redis → Key-value database → NoSQL database management system**

This is the crucial structure that makes semantic search possible.

### 10. Basic semantic search

Instead of asking:

> “Which articles contain the words ‘NoSQL database’?”

the system can ask:

> “Which articles are associated with the concept ‘NoSQL database management systems’?”

This means the search is based on the graph's understanding of the domain rather than simply matching text.

### 11. Semantic expansion of search results

The ontology allows the search to expand beyond directly matching concepts.

For example:

* NoSQL database management systems

  * Key-value databases

    * Redis

An article about **Redis** might therefore be returned for a search about **NoSQL databases**, even if the article never contains the phrase “NoSQL database.”

This is one of the central benefits demonstrated.

### 12. Graph traversal makes the expansion possible

* Neo4j/Cypher can traverse relationships in the ontology.
* A query can specify how far it should traverse.
* For example:

  * 0 levels → exact concept.
  * 1 level → immediate related concepts.
  * 2 levels → concepts further down/up the hierarchy.
  * `*`/variable-length paths → potentially arbitrary depth.
* This gives the application control over how broadly semantic search expands.

### 13. Semantic search can explain its results

A particularly important point was **explainability**.

Instead of merely returning an article, the system can show why it was considered relevant.

For example:

**Article → Redis → Key-value database → NoSQL database**

Therefore:

> This article is relevant because it discusses Redis, which is a key-value database, which is a type of NoSQL database.

The graph provides an explicit path explaining the recommendation/search result.

### 14. Semantic search can become recommendation

The same graph can be used for **“Read Next” recommendations**.

Instead of starting with a search query:

* Start with the article the user is currently reading.
* Find the concepts associated with that article.
* Find other articles associated with the same or related concepts.
* Recommend those articles.

Thus, semantic search and content recommendation can use essentially the same underlying graph.

### 15. Personalization

Because the relationships are explicit, recommendations can be customized.

For example:

* Recommend articles related to NoSQL.
* But exclude articles related specifically to key-value databases.
* Or restrict traversal to a certain number of levels.

This gives developers explicit control over how recommendations are generated.

### 16. The quality of the ontology matters

A major caveat was demonstrated.

The Wikidata taxonomy classified Neo4j under categories such as **free software/proprietary software**.

That could result in recommendations based on relationships that aren't particularly useful for the application's purpose.

The lesson was:

> **The quality and relevance of the ontology directly affects the quality of semantic search and recommendations.**

Having a graph alone isn't enough; the domain knowledge represented in it needs to make sense for the use case.

### 17. You can create your own ontology

* You aren't restricted to Wikidata.
* An organization can create its own domain ontology.
* The ontology can represent knowledge specific to its business or application.
* It can then be imported into Neo4j using standards such as RDF, SKOS or OWL.

### 18. Multiple ontologies can coexist

The demo then added another ontology describing **technology stacks**.

Examples included:

* GRANDstack → GraphQL + React + Neo4j + Apollo.
* MEAN stack → MongoDB + Express + Angular + Node.
* LAMP stack → Linux + Apache + MySQL + related components.

This ontology was imported alongside the Wikidata-based ontology.

The important point was that **multiple sources of domain knowledge can coexist and be connected in the same graph**.

### 19. Ontologies are composable

* Existing public ontologies can be combined with internally created ones.
* You don't have to duplicate information that already exists elsewhere.
* Shared identifiers/URIs can allow concepts from different ontologies to connect.
* Adding another ontology effectively gives the search system additional paths through the knowledge graph.

### 20. The ontology can evolve dynamically

One of the important architectural points was that the query logic doesn't necessarily need to change when the knowledge changes.

You can:

* Add concepts.
* Remove concepts.
* Add relationships.
* Modify classifications.
* Add new technology stacks.
* Continuously update domain knowledge.

The existing graph queries can automatically use the new relationships.

So the **data/knowledge changes while the search logic remains the same**.

### 21. Public + internal knowledge

The presenters suggested combining:

* Publicly available ontologies/concept schemes.
* Organization-specific knowledge.
* Internal terminology.
* Internal relationships between concepts.

This can make the semantic search much more relevant to a particular organization's domain.

### 22. Industry-specific ontologies

* Some industries already have extensive ontologies.
* Health and life sciences were given as an example.
* Organizations shouldn't necessarily rebuild established domain ontologies.
* Instead, they can reuse existing standards and enrich/customize them with organization-specific knowledge.

### 23. What the end-user experience might look like

Although the demo used Neo4j Bloom to visualize the graph, the end user probably wouldn't need to see the entire graph.

A normal application could simply show:

**Read Next**

* Article A
* Article B
* Article C

The graph traversal and semantic reasoning happen behind the scenes.

The graph visualization is particularly useful for developers/data specialists who need to understand **why** a result was produced.

### 24. Semantic search vs. machine learning

The session also touched on combining explicit knowledge with machine learning.

The ontology in the demonstration was **curated**:

* Someone explicitly defined relationships such as “Redis is a key-value store.”
* Someone explicitly defined the components of the GRANDstack.

But relationships could potentially also be **learned from the documents**.

Possible approaches mentioned:

* Analyze topic co-occurrence.
* Measure similarities/overlap between topics.
* Learn taxonomies from a corpus of articles.
* Combine machine learning with explicitly defined semantics.

### 25. Digital twins

Digital twins were briefly discussed as a possible future topic.

The description given was essentially:

* A digital twin is a software representation/replica of a real-world environment or system.
* It can be used to simulate, understand, analyze, or predict behavior.
* Ontologies can help formally describe the domain represented by the digital twin.
* Graphs can therefore play an important role in digital-twin systems.

### 26. The central takeaway

The session's core argument can be condensed to:

**Traditional search:**
`Text → keyword match → documents`

**Semantic search:**
`Documents → entities → ontology/domain knowledge → graph traversal → relevant documents`

And the key idea behind semantics was summarized as:

> **Make your knowledge about a domain explicit, put that knowledge into a graph, and then navigate it.**

That explicit knowledge is what allows the system to find relationships and results that **pure keyword matching would miss**.

# Broadcast 3: Apr 5

Here are the main points made in the session, organized by topic.

## 1. Purpose of SHACL

* **SHACL** is used to define and validate the expected **shape/structure of a graph**.
* It allows you to express constraints **declaratively**, rather than writing many custom Cypher queries.
* A SHACL engine can execute those constraints against a Neo4j graph.
* SHACL can be used for:

  * Data-quality validation.
  * Structural validation.
  * Enforcing rules on data.
  * Reporting violations after data has been loaded.
  * Preventing invalid data from being committed.

## 2. Examples of constraints SHACL can express

SHACL can specify things such as:

* A property must match a **regular expression**.

  * Example: a customer's phone number must follow a particular format.
* A relationship must have a certain **cardinality**.

  * Example: a product must have at least 3 suppliers.
* A property must have a particular number of values.

  * Example: a supplier must have exactly one name.
* A property must have a particular **datatype**.

  * Example: product name must be a string.
* A numeric value must fall within a **minimum/maximum range**.

  * Example: product price must be between 10 and 100.
* A relationship's target nodes must have a particular type.

  * Example: `supplied_by` must connect a product to a `Supplier`.
* A property can be restricted to an **enumerated list**.

  * Example: supplier country must be one of a defined set of valid countries.
* A node can have a **closed shape**.

  * This means only explicitly allowed properties are permitted.

## 3. What "shape" means

The speaker uses "structure" in two senses:

### Internal structure

The structure of an individual node or relationship:

* Labels/types.
* Properties.
* Property values.
* Datatypes.
* Cardinalities.

### External structure

How things are connected in the graph:

* Which nodes can connect to which other nodes.
* Relationship types.
* Relationship cardinality.
* Types of nodes at the other end of relationships.

So SHACL can describe both **what an entity looks like** and **how entities can be connected**.

## 4. SHACL vs ontology

A major distinction was made between **SHACL and ontologies**.

### Ontology

An ontology describes a domain and its semantics.

For example:

> Customer → purchases → Product

An ontology can allow an inference such as:

> If something purchases a product, it can be inferred to be a customer.

The ontology is therefore primarily **descriptive and inference-oriented**.

It does not necessarily prevent invalid structures from being created.

For example, you could theoretically create a `Cat` that purchases a product. An ontology could infer that the cat is a customer based on the defined semantics.

### SHACL

SHACL is primarily about **constraints and validation**.

It describes:

> "This is what the graph is supposed to look like."

It can then detect or prevent data that violates those rules.

### Key distinction

**Ontology → describes the domain and enables inference.**

**SHACL → describes expected structure and validates/enforces it.**

If you already have an ontology, such as an OWL ontology, you may need to **translate it into SHACL shapes** before using it as a validation mechanism.

## 5. Data model, schema, and ontology are different concepts

The discussion emphasized that these can be thought of as different **layers of abstraction**:

* **Data model** → how data is represented.
* **Schema/shape** → what structures are allowed or expected.
* **Ontology** → what entities and relationships mean and what can be inferred from them.

An ontology can therefore exist alongside SHACL rather than being a replacement for it.

## 6. SHACL originated in the RDF world

* SHACL was designed for **RDF graphs**.
* Neo4j can nevertheless use SHACL because RDF and property graphs can be mapped/serialized between representations.
* Neo4j's **Neosemantics (n10s)** plugin provides the functionality for working with RDF and SHACL.

## 7. SHACL uses RDF/Turtle syntax

The example uses **Turtle**, a human-readable RDF serialization.

Other RDF serializations mentioned include:

* RDF/XML
* JSON-LD
* N-Triples
* Turtle

The SHACL definition contains several kinds of namespaces.

### SHACL namespace

Used for SHACL vocabulary such as:

* `NodeShape`
* `property`
* `datatype`
* `pattern`
* `minCount`
* `maxCount`
* `class`
* `in`
* etc.

### XSD namespace

Used for datatypes such as:

* string
* integer
* date
* etc.

### Neo4j namespace

Used to refer to the actual labels/properties in a **native Neo4j property graph**.

### Custom/example namespace

An arbitrary namespace can be used to uniquely identify your own shapes.

## 8. Example of a SHACL node shape

A shape can say something conceptually like:

> For every `Product` node, the `productName` property must be a string, have at most one value, and match a particular regular expression.

The shape therefore associates:

**Node type → property/relationship → constraints**

For example:

```text
Product
  └── productName
       ├── datatype = string
       ├── maxCount = 1
       └── pattern = regular expression
```

An important detail discussed was:

* `maxCount = 1` does **not** mean the property is required.
* Without `minCount`, zero values can still be valid.

So:

```text
maxCount = 1
```

means:

> zero or one value

whereas:

```text
minCount = 1
maxCount = 1
```

means:

> exactly one value.

## 9. Properties and relationships use similar SHACL syntax

In RDF, properties and relationships are both represented through triples.

Therefore SHACL's `property` structure can be used for both.

In Neo4j, the constraint could refer to:

* A normal node property.
* A relationship.

For example:

```text
Product
  └── supplied_by
        └── Supplier
```

A shape could require:

* `supplied_by` to point to `Supplier` nodes.
* At least 2 suppliers.
* Potentially a maximum number of suppliers.

## 10. SHACL and GraphQL are different

The discussion compared SHACL with GraphQL.

### GraphQL

GraphQL primarily defines an **API contract**:

* What the API exposes.
* Entry points.
* Fields.
* Arguments.
* Query structure.
* Filtering capabilities.

### SHACL

SHACL focuses more on **data validation and graph structure**.

For example, SHACL can directly express constraints such as:

* Minimum/maximum numeric values.
* Regular expressions.
* Cardinality.
* Datatypes.
* Allowed values.

GraphQL can sometimes achieve similar functionality through **schema directives/extensions**, but those typically require corresponding application/server-side logic to enforce the rules.

## 11. SHACL can be extended

SHACL is extensible.

Vendors can add their own functionality, provided their SHACL engine implements the associated logic.

The speaker mentioned the possibility of extensions involving things such as:

* Cypher selectors.
* Vendor-specific functionality.

However, custom SHACL extensions are not necessarily as easy to create for an individual project as GraphQL application-level extensions.

## 12. Where validation happens is a choice

Validation does not necessarily have to happen in only one place.

Possible locations include:

* Database.
* Application.
* Client.
* Data ingestion pipeline.
* Frontend/UI.

The benefit of SHACL is that the **same declarative definition** can potentially be reused in different places.

The Neo4j/Neosemantics implementation focuses on executing SHACL validation **inside the database**.

## 13. Example Neo4j setup

The hands-on example used:

* An empty local Neo4j database.
* The **Neosemantics** plugin.
* A Northwind-style dataset.
* Neo4j Data Importer.
* SHACL definitions stored in a GitHub repository.
* NeoDash for visualization.

The example graph contained things like:

```text
Customer → Order → Product
Product → Supplier
Product → Category
```

## 14. Loading SHACL shapes

Neosemantics provides ways to import SHACL definitions.

Two approaches were demonstrated conceptually:

### Inline

Pass the SHACL/Turtle content directly to the procedure.

Useful for:

* Small fragments.
* Testing.
* Examples.

### Fetch

Give Neosemantics a URL containing the SHACL definition.

Useful for:

* Complete shape files.
* Reusable definitions.
* GitHub-hosted shapes.

## 15. Shapes become executable after loading

When SHACL shapes are imported:

1. They are ingested into Neo4j.
2. They are compiled into an executable form.
3. They become the **currently active shapes**.
4. The graph can then be validated against them.

Neosemantics can also list the currently loaded shapes.

## 16. Validation can cover the entire graph or a subset

Three validation approaches were discussed:

### Normal validation

Runs all currently active shapes against the graph.

### Validation of a set

Validates only a specified collection of nodes.

This is useful when you don't want to validate the entire database.

### Transactional validation

Validates changes as part of a transaction.

This is the enforcement mechanism.

## 17. Non-transactional validation is a "soft constraint"

The basic validation approach does **not prevent invalid data from entering the database**.

Instead:

1. Data is written.
2. Validation is run.
3. Violations are reported.

This is useful when you want to:

* Audit data.
* Generate reports.
* Find existing problems.
* Clean up data later.

## 18. Example validation violation

The example defined a regular expression for supplier `CompanyName`.

One supplier had a value containing `%`, which violated the pattern.

The validation result identified things such as:

* The affected node.
* Node type.
* Shape identifier.
* Violated shape.
* Constraint type.
* Offending value.
* Property containing the value.
* Severity.
* Validation message.

So the output explains **why the data is invalid**, rather than simply saying that something failed.

## 19. Cardinality violations are also detected

The speaker then deliberately modified a supplier so that it had **two `CompanyName` values**.

The shape specified:

```text
maxCount = 1
```

Running validation again produced another violation.

The result indicated that:

> the cardinality was 2 when only 1 was allowed.

This demonstrates that the SHACL engine dynamically evaluates the graph against the loaded constraints.

## 20. Transactional validation can enforce constraints

This is the stronger mode.

A Neo4j database trigger can call a Neosemantics transactional validation function.

Conceptually:

```text
Transaction
     ↓
Database trigger
     ↓
SHACL validation
     ↓
Valid? ── Yes → Commit
          No  → Reject transaction
```

The trigger passes the changed parts of the transaction to the validator, including:

* Created nodes.
* Modified properties.
* Added/changed data.
* Other relevant changes.

## 21. Invalid transactions can be rejected

The example was:

> An actor is supposed to act in a movie.

A write attempted to connect the actor to something that was not a movie.

The transactional SHACL validation:

* Detected the violation.
* Raised an exception.
* Rejected the transaction.
* Prevented the invalid state from being committed.

So SHACL can function as a **hard constraint**, not merely a reporting mechanism.

## 22. Soft vs hard validation

The presentation effectively described two modes:

| Mode                     | Behavior                           |
| ------------------------ | ---------------------------------- |
| Regular validation       | Find and report violations         |
| Transactional validation | Reject changes that violate shapes |

The important point is that **both use the same SHACL definitions**.

You don't need to create separate rules for reporting versus enforcement.

## 23. Security/architecture decision depends on requirements

When asked which validation method is recommended for security/vulnerability reasons, the answer was essentially:

* There isn't one universal choice.
* Both approaches are valid.
* The decision depends on the application's requirements.
* You should understand the tradeoffs between validation approaches and choose accordingly.

## 24. Enumerated values

SHACL can restrict a property to an explicit list of valid values.

For example:

```text
country ∈ {UK, USA, Germany, France, ...}
```

This uses the SHACL `in` constraint.

A value outside the allowed list becomes invalid.

## 25. Closed shapes

A **closed shape** restricts the allowed structure of a node.

For example, suppose a supplier is defined with:

```text
CompanyName
Country
```

A closed shape can say:

> These are the permitted properties; other properties aren't allowed.

This is stronger than merely saying:

> "If CompanyName exists, it must be a string."

It controls the **overall structure** of the node.

## 26. SHACL can be used with imported RDF

Neo4j can import RDF using Neosemantics while preserving namespaces.

This means SHACL can be applied to:

* A native Neo4j property graph.
* A graph derived from RDF.
* Namespace-aware RDF-derived data.

For a native Neo4j graph, the Neo4j namespace is used to identify labels and properties.

## 27. Large shape sets can be loaded at once

Instead of importing one small SHACL fragment, the complete Northwind SHACL definition can be fetched from a URL.

The same validation process then operates over the larger set of constraints.

The demonstration produced **124 violations** in the example graph.

## 28. Violations can be visualized with NeoDash

The session used **NeoDash** to create a dashboard.

The dashboard showed:

* Currently active shapes.
* Number/type of violations.
* Minimum-cardinality violations.
* Maximum-cardinality violations.
* Pattern violations.
* Detailed violation information.

The underlying dashboard is essentially powered by **Cypher queries** over the validation information.

## 29. Neo4j's surrounding ecosystem is important

The presenters highlighted how several tools can work together:

* **Neosemantics** → RDF and SHACL.
* **Data Importer** → visually create a graph model and import CSV data.
* **NeoDash** → visualize graph data and validation results.
* **APOC** → conveniently create database triggers.

The overall idea is that these tools reduce the amount of custom code required.

## 30. Existing ontologies can be turned into validation rules

If an organization already has an ontology such as:

* FIBO for finance.
* schema.org.
* Another domain ontology.

The proposed workflow is:

```text
Existing OWL ontology
        ↓
Translate into SHACL shapes
        ↓
Import shapes into Neo4j
        ↓
Validate/enforce graph
```

The important distinction remains that the ontology itself isn't necessarily the enforcement mechanism.

## 31. Current limitation: shape sets overwrite one another

One limitation mentioned was that loading a new set of shapes currently tends to **overwrite the existing active shape set**.

A requested improvement is more granular/incremental management.

For example:

```text
Team A → owns Supplier shapes
Team B → owns Product shapes
Team C → owns Customer shapes
```

The goal would be to allow these shape sets to coexist without one replacing another.

## 32. Future possibility: expose active shapes

Another planned capability is to expose the currently active SHACL shapes from the graph.

That could allow applications to use the same definitions for things such as:

* Client-side validation.
* Form generation.
* UI generation.
* Data ingestion validation.
* External validation pipelines.

This would support a model of:

```text
One SHACL definition
        ↓
Database validation
Client validation
UI generation
Data pipeline validation
```

## 33. Future possibility: generate SHACL from visual graph models

One major usability issue identified was that writing SHACL directly in RDF/Turtle can be cumbersome.

A proposed solution is to take an existing visual model from tools such as:

* Neo4j Data Importer.
* Arrows.

and automatically generate the **skeleton of a SHACL definition**.

For example:

```text
Visual graph model
       ↓
Generated SHACL skeleton
       ↓
Developer fills in:
  - cardinalities
  - regex patterns
  - value constraints
  - other rules
```

This wouldn't necessarily generate every constraint automatically, but it would eliminate much of the work of writing the shape from scratch.

## 34. Longer-term idea: visual SHACL editor

An even more ambitious idea is a UI where users could:

* Start with a graph model.
* Generate the SHACL structure.
* Select constraint types from dropdowns.
* Enter values for those constraints.
* Generate the final SHACL definition.

This was presented as more aspirational rather than an immediately available feature.

## 35. Docker deployment

For Docker-based deployments, the suggested approach was:

1. Install/enable **Neosemantics** in the Neo4j Docker deployment.
2. If using transactional triggers, also install **APOC**.
3. Use an initialization script.
4. Run the SHACL import when the database starts.
5. Potentially fetch the SHACL definitions directly from GitHub.
6. Use something like Cypher Shell from the initialization script.

Conceptually:

```text
Docker starts Neo4j
        ↓
Install/load Neosemantics (+ APOC if needed)
        ↓
Init script runs
        ↓
n10s validation import
        ↓
SHACL shapes become active
        ↓
Database is ready with validation rules
```

## 36. Overall takeaway

The central message of the presentation is:

> **SHACL provides a declarative way to describe what a Neo4j graph should look like, and Neosemantics allows those definitions to be used for validation and enforcement.**

The important distinction is:

**Ontology**
→ describes meaning and supports inference.

**SHACL**
→ describes constraints and validates/enforces structure.

**Neo4j**
→ stores the property graph.

**Neosemantics**
→ brings RDF/SHACL capabilities into Neo4j.

**APOC triggers**
→ can make SHACL validation transactional.

**NeoDash**
→ can visualize validation results.

And the same SHACL definition can support either **"tell me what's wrong"** validation or **"don't allow this to happen"** enforcement.
