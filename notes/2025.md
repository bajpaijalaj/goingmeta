# Broadcast 5: Jan 7 - One Ontology To Rule Them All: Building KG from Mixed Data (https://youtube.com/live/0c3WicsmLuo)

Here are the main points made in the episode, organized by topic:

### 1. Episode focus: combining structured and unstructured data

* The episode focuses on **knowledge graph construction from mixed data**.
* “Mixed data” means combining:

  * **Structured data** — CSV files, relational databases, tables, etc.
  * **Unstructured data** — PDFs, free-text documents, product descriptions, credit notes, etc.
* The central idea is to use **one common ontology** to drive the construction of the knowledge graph from both types of data.
* This reflects an enterprise reality where information is spread across many different sources but needs to be represented using a common domain model.

### 2. Ontology as the common model

* An ontology is described as a **formal, machine-readable representation of a domain**.
* It can range from a simple schema containing:

  * Entities/classes
  * Relationships
  * Properties/attributes
* More sophisticated ontologies can also contain:

  * Taxonomies
  * Constraints
  * Actions
  * Other semantic information
* The ontology acts as the **target model or blueprint** for the knowledge graph.
* Using a common ontology helps maintain:

  * Consistency
  * Alignment
  * Reusability
  * Interoperability

### 3. Different representations of an ontology

* Ontologies can be represented using **W3C standards**, such as:

  * OWL
  * RDFS
  * RDF vocabularies
* The ontology doesn't have to originate in a particular tool.
* A machine-readable ontology can be transformed into other representations and models.
* The episode demonstrates converting a W3C ontology into a **graph model that can be imported into Neo4j Aura's model catalog**.
* Conversely, a graph model created in Neo4j can be converted back into an RDF/W3C representation.

### 4. Neo4j Aura Graph Model / Model Catalog

* Neo4j Aura has a **Graph Models / Model Catalog** capability.
* A graph model can be created manually by defining:

  * Nodes/entities
  * Relationships
  * Properties
* The model can then be saved in the catalog and used to drive data ingestion.
* More importantly, the model can be **generated from an existing ontology**, avoiding the need to recreate the model manually.
* This allows an existing industry or enterprise ontology to become the basis for a Neo4j knowledge graph.

### 5. Reusing existing/public ontologies

* The presenters emphasize that organizations should **reuse existing ontologies where possible rather than reinventing them**.
* Examples shown include:

  * An insurance ontology
  * A building/construction ontology
* Public ontologies can provide a starting point for modeling a domain.
* An imported ontology can also be **extended or modified** to accommodate an organization's specific requirements.
* Using an established ontology can help with interoperability because the resulting graph follows an existing standard.

### 6. Ontology → Neo4j graph model

The demonstrated workflow is roughly:

**W3C ontology → parse ontology → select relevant classes → generate JSON graph model → import into Neo4j Aura → use model for data ingestion**

* The demo application takes an ontology URL.
* It scans the ontology and identifies its classes and properties.
* Users can select which classes they actually need.
* The application generates a JSON representation of the selected model.
* That model is imported into the Neo4j Aura Graph Model catalog.
* The resulting model contains the ontology's entities, relationships and properties.

### 7. Example: sales ontology

The main demonstration uses a **sales domain**.

The ontology contains concepts such as:

* Product
* Customer
* Purchase
* Location
* Credit Note
* Store

Relationships include concepts such as:

* Purchase → customer
* Purchase → product
* Credit Note → purchase
* Customer → location

Properties include things such as:

* Customer ID
* Customer name
* Email
* Product code
* Product name
* Purchase date
* Quantity
* Credit note date
* Refund amount

### 8. Structured data ingestion

The structured data consists of several CSV files, including:

* Customers
* Purchases
* Locations

The Neo4j data importer is used to map the CSV fields to the ontology/model.

For example:

* `customer_id` → Customer ID
* `full_name` → Customer name
* `email` → Customer email
* Purchase ID → Purchase identifier
* Quantity → Purchase quantity
* Product ID → Product identifier

Foreign keys in the relational data are used to establish relationships between the graph entities.

### 9. The structured data is incomplete

* An important point in the demo is that the structured data doesn't contain all the information needed by the ontology.
* For example, the purchase data contains only limited information about products.
* Additional product information exists in **unstructured PDF documents**.
* Similarly, credit-note information isn't present in the structured CRM data.
* Therefore, the graph needs to be assembled from multiple sources.

### 10. Using GraphRAG for unstructured data

* The presenters then use the **Neo4j GraphRAG Python package** and its Knowledge Graph Builder pipeline.
* The pipeline processes PDFs by:

  1. Loading documents
  2. Parsing them
  3. Splitting them into chunks
  4. Creating embeddings
  5. Extracting entities
  6. Extracting relationships
  7. Writing the resulting information into the knowledge graph

### 11. Two graphs are produced from the unstructured data

The GraphRAG process creates two conceptual layers:

**Lexical/document graph**

* Documents
* Chunks
* Text
* Embeddings
* Relationships between documents and chunks

This supports retrieval approaches such as vector search.

**Domain/knowledge graph**

* Extracted entities
* Relationships between entities
* Domain-specific properties

The domain graph is the more important part for the ontology-driven knowledge graph.

### 12. The ontology provides the GraphRAG guardrails

This is one of the central technical points.

Instead of letting an LLM freely decide what entities and relationships to extract, the ontology supplies:

* Allowed entities
* Allowed relationships
* Properties
* Potential connections between entities

The GraphRAG pipeline therefore uses the ontology as a **schema/guardrail for extraction**.

Conceptually:

**Ontology → extraction schema → LLM extraction → knowledge graph**

This makes the generated graph more controlled and aligned with the intended domain model.

### 13. Combining structured + unstructured data

After both ingestion processes are complete:

* Structured CRM data exists in the graph.
* Unstructured PDFs have contributed additional entities and relationships.
* Because both were constructed according to the **same ontology**, they can connect naturally.

For example:

**Credit Note → Purchase → Customer → Location**

Some of the information in that chain comes from the PDFs, while other information comes from the CRM/CSV data.

The ontology provides the common structure that allows the two sources to connect.

### 14. Why this approach is useful

The presenters highlight several benefits:

* A single model can govern multiple data sources.
* Data from different systems can be brought together consistently.
* Less reliance on unconstrained LLM-generated schemas.
* Greater consistency and potentially fewer extraction/modeling errors.
* Easier interoperability with other systems.
* Ability to reuse established industry standards.
* Easier modeling when you don't know how to design the graph from scratch.

### 15. Ontologies don't have to be complete

* An imported ontology should be treated as a **starting point**, not necessarily a finished model.
* An organization may:

  1. Find an existing ontology.
  2. Import it.
  3. Keep the relevant parts.
  4. Add its own concepts and relationships.
* This lets organizations benefit from existing standards while adapting them to their own domain.

### 16. Finding existing ontologies

A question is raised about pre-existing ontologies for areas such as:

* Expense management
* Procurement
* Life sciences
* Pharma
* Construction

The response is that repositories and catalogs exist, but finding suitable ontologies can still require significant research.

Important considerations when selecting one include:

* How recently it has been updated
* How widely it is used
* Whether it is actively maintained
* Whether other projects use it
* How well it matches the intended domain

### 17. Multiple ontologies can potentially be combined

* The discussion notes that multiple ontologies can be imported and their relevant portions combined into a graph model.
* For example, one ontology could provide a people/customer concept while another provides product concepts.
* Only the portions relevant to the particular application need to be retained.

### 18. Why convert the ontology to JSON?

A question asks why the ontology isn't simply imported directly in Turtle/RDF format.

The explanation is that the demonstrated intermediate JSON step allows the process to:

* Parse the ontology.
* Select only relevant classes.
* Select the required portion of the model.
* Generate a Neo4j-compatible graph model.

The RDF/Turtle representation remains the standard ontology serialization; JSON is simply part of the demonstrated import workflow.

### 19. Ontology vs. Pydantic constraints

A Q&A discussion distinguishes **ontology modeling** from **validation constraints**.

* Ontologies primarily describe the domain/schema:

  * Classes
  * Relationships
  * Properties
* They aren't necessarily equivalent to the detailed validation constraints you might define with Pydantic.
* For richer RDF-based constraints, the presenters mention **SHACL**.
* Examples of constraints include requirements such as:

  * A relationship must exist.
  * A relationship can occur a minimum/maximum number of times.
  * A property must follow a particular format.
* Therefore:

  * **Ontology ≈ domain/schema description**
  * **SHACL/Pydantic ≈ validation/constraints**

### 20. Ontologies can be modified inside Neo4j

* Once a graph model is imported into Neo4j, it can be modified.
* Elements can be:

  * Added
  * Removed
  * Extended
* The important architectural question is then deciding which representation is the **master/source of truth**.
* An organization needs to establish an ontology lifecycle and versioning strategy.

### 21. Closing the circle

The episode demonstrates that the workflow can work in both directions:

**Ontology → Neo4j model → graph**

and

**Neo4j model → RDF/W3C ontology representation**

Therefore, the starting point doesn't necessarily have to be an external ontology.

You could:

* Start with a formal ontology.
* Start with a Neo4j graph model.
* Transform between representations.
* Use the resulting model to drive data ingestion.

### 22. Ontologies and reasoning

The final Q&A touches on:

* Decision-rule engines
* Solvers
* Forward chaining
* Backward chaining
* Inferencing

The presenters point out that ontologies can also be used for **reasoning/inference**, beyond simply providing a schema.

They refer viewers to an earlier episode on **“Reasoning 101”** for this topic.

### 23. SQL databases → ontologies

Another question asks about tools for going from SQL databases to ontologies.

The discussion distinguishes between:

* Creating an ontology from a relational schema.
* Mapping an existing relational database to an existing ontology.

They mention an earlier approach using an LLM to derive an ontology/schema from a relational database and note that other ontology/data-mapping tools also exist.

### 24. Overall workflow demonstrated

The whole episode can essentially be reduced to this:

**Existing ontology**
↓
**Convert/import it into a Neo4j graph model**
↓
**Use the model to map structured data**
↓
**Use the same ontology as the extraction schema for unstructured data**
↓
**Build the knowledge graph**
↓
**Automatically connect information from both sources**
↓
**Query the combined graph**

### 25. Main takeaway

The core message of the episode is:

> **Create or reuse an ontology once, then use that common model to control both structured-data ingestion and LLM-based extraction from unstructured data.**

This provides a more consistent way to construct a knowledge graph from enterprise data that comes in many different forms.

# Broadcast 6: Feb 4 - Retrieval Methods Compared (https://youtube.com/live/GPmHpp3QEWc)

Here are the main points made in the transcript, organized by topic:

### 1. Episode purpose

* This episode is a **Q&A and feedback session** rather than a completely new topic.
* The hosts wanted to:

  * Recap the previous episode.
  * Explain the parts that were covered too quickly.
  * Answer questions collected from the community.
  * Take live questions from viewers.
* Viewers watching later were encouraged to leave questions in the YouTube comments, Discord, or community forums.

### 2. Recap: Knowledge Graph + RAG

* Previous episodes focused on:

  * Knowledge graph construction.
  * Knowledge Graph Builder.
  * GraphRAG.
  * Combining structured and unstructured data.
* The central concept is an **ontology/domain schema** that acts as a common model for different data pipelines.
* The example used a sales dataset containing:

  * Customers.
  * Purchases/orders.
  * Products.
  * Locations.
  * Credit notes/refunds.
* Structured data came from a CRM.
* Unstructured data came from PDFs such as:

  * Product descriptions.
  * Credit/refund notes.
* The same ontology was used to guide both structured-data ingestion and unstructured-data extraction.

### 3. Why the ontology matters

* Without guidance, an automatic knowledge graph can produce a graph that is difficult to use.
* The ontology provides **guardrails/scaffolding** by defining:

  * Entity types.
  * Relationships.
  * Labels.
  * Properties.
  * Terminology.
  * Unique identifiers.
* This helps different data-ingestion pipelines create a **consistent, unified graph**.
* The ontology can be created first and then converted into the formats required by different tools.
* Alternatively, the schema can be defined directly in code.

### 4. What GraphRAG adds to ordinary vector RAG

* Ordinary vector RAG:

  * Converts text into embeddings.
  * Searches for similar vectors.
  * Returns the most similar chunks to an LLM.
* The limitation is that similarity alone may return information that is relevant but incomplete.
* GraphRAG combines:

  * Vector search.
  * Explicit entities.
  * Relationships.
  * Structured data.
  * Graph traversal.
* This allows retrieved information to be **contextualized by navigating the graph**.
* GraphRAG can therefore support multiple retrieval patterns, including:

  * Vector search.
  * Vector search + graph traversal.
  * Text-to-Cypher.
* Sometimes the vector index can even be bypassed and a structured query can be generated directly.

### 5. The two-layer graph

The demonstrated graph contains two complementary parts:

* A **lexical/vector layer**:

  * Documents are split into chunks.
  * Chunks contain text.
  * Text is converted into embeddings.
  * Embeddings are stored in a vector index.
* A **domain/entity layer**:

  * Entities such as products, customers, purchases, and credit notes are extracted.
  * These entities are connected through relationships.

This means a document chunk can be connected to a real product, customer, order, etc.

### 6. Combining CRM data with unstructured documents

* CRM data contained relatively limited product information, such as product IDs.
* Product-description documents contained much richer information:

  * Product specifications.
  * Features.
  * Details.
  * Other descriptive text.
* Credit notes contained information such as:

  * Credit-note ID.
  * Date.
  * Customer.
  * Address.
  * Purchase/order reference.
  * Refund amount.
  * Refund reason.
* Credit notes could therefore be linked to customers, products, and purchases.

### 7. Entity resolution problem

* Data from different sources does not always use identical identifiers.
* Example:

  * One source used a product identifier like `catcore_000459`.
  * Another source used only `459`.
* Because the identifiers weren't exactly identical, automatic merging didn't occur.
* The hosts demonstrated a small Cypher transformation to:

  * Remove the prefix.
  * Remove leading zeros.
  * Convert the value into a comparable representation.
* Once the identifiers matched, the two product nodes could be merged.

### 8. APOC and merging nodes

* APOC was used to simplify graph operations.
* `mergeNodes` can combine two or more nodes into one.
* It can also control how:

  * Properties are handled.
  * Relationships are handled.
  * The merge takes place.
* APOC provides many utility procedures/functions that would otherwise require more Cypher code.
* The hosts noted the distinction between **APOC Core and APOC Extended**, because some functions are available only in Extended.

### 9. Result: connected structured + unstructured graph

After resolving the product IDs:

* Structured data and unstructured data became connected.
* A possible path could go from:

  * Product description → product → purchase → credit note
  * Or between other combinations of structured and unstructured entities.
* This creates a graph through which an application can navigate between information from different sources.

### 10. Three retrieval approaches demonstrated

#### A. Vector Retriever

* The simplest approach.
* The question is converted into an embedding.
* The vector index is searched.
* The top-N similar chunks are returned.
* The LLM generates an answer from those chunks.
* Example question:

  * “What do you know about smart watches?”
* The approach worked well for relatively straightforward questions about product descriptions.

#### B. Vector + Cypher Retriever

* Starts with vector search.
* The resulting nodes are then used as starting points for graph traversal.
* Additional structured information can be retrieved from connected nodes.
* Example:

  * Find a product from its description.
  * Traverse to purchases.
  * Count sales.
  * Traverse to credit notes.
  * Count returns.
* This can answer richer questions such as customer satisfaction around a product.
* Example result:

  * A portable charger had a sales count of 130 and four returns.
* A limitation is that the Cypher retrieval query is **hardcoded**.
* The hosts suggested that future agentic RAG approaches could expose multiple retrieval tools and let the LLM decide which one to use.

#### C. Text-to-Cypher Retriever

* Instead of searching a vector index, the system asks an LLM to generate a Cypher query.
* The LLM needs the database schema/ontology as context.
* The process is:

  1. User asks a natural-language question.
  2. The ontology/schema is provided to the LLM.
  3. The LLM generates Cypher.
  4. The Cypher query is executed.
  5. The result is returned.
* Example:

  * “How many orders have been returned for products with AI functionality in their features?”
* The generated Cypher identified products, purchases, credit notes, and the relevant product features, then counted the matching results.
* The example returned **five**.
* There can be variability in how the LLM interprets terms such as “AI functionality,” so generated queries may not always behave identically.

### 11. Controlling what information reaches the LLM

* A **result formatter** can determine what information retrieved by Cypher is passed to the LLM.
* It can include:

  * Node properties.
  * Relationship information.
  * Properties of neighboring nodes.
  * Paths.
  * Aggregated values.
  * Metadata.
* This provides control over how much context is sent to the generation step.

### 12. Controlling the number of vector matches

* For vector retrieval, the application can specify the number of top results to return.
* For example:

  * Top 2.
  * Top 3.
  * Top 5.
* Vector indexes can use similarity measures such as:

  * Euclidean distance.
  * Cosine similarity.
* There isn't inherently a priority between a node's value and its other properties during vector search; the indexed/vectorized property is what is searched.
* Additional filtering can be performed afterward using Cypher.

### 13. LLM choice

* The demonstration used OpenAI models, mainly for demonstration purposes.
* The hosts emphasized that GraphRAG isn't restricted to OpenAI.
* Other supported options can be used, including:

  * Azure-hosted models.
  * Local models such as those run through Ollama.
* The choice of embedding and generation model is configurable.

### 14. GraphRAG vs LangChain

* A viewer asked about LangChain's Neo4j graph Q&A functionality.
* The answer was that **both approaches are valid**.
* LangChain may be preferable for developers already familiar with its APIs.
* The Neo4j GraphRAG package provides another way of implementing the same general retrieval concepts.
* The Neo4j team is working toward better organization and ongoing maintenance of the integration.

### 15. Comparing RAG approaches

* Performance shouldn't simply be judged from one or two examples.
* A proper evaluation requires a collection of questions and expected answers.
* The hosts compared this conceptually to **unit testing**.
* Useful evaluation frameworks include **RAGAS**.
* Evaluation can consider things such as:

  * Whether the answer contains the expected information.
  * Whether it contains unnecessary noise.
  * Whether retrieval is relevant.
* Quantifying the benefit of a RAG architecture is important when justifying its cost to customers.

### 16. When to move from a relational database to a graph

* The hosts explicitly said there is **no universal answer**.
* They would not recommend automatically moving all relational data into a graph.
* One option is to leave the original data where it is and use a graph as a **semantic layer**.
* The semantic layer can describe:

  * Entities.
  * Ontology.
  * Relationships.
  * Where data is stored in underlying systems.
* For example, the graph could say that customer information comes from a particular relational table or document collection.
* A retrieval system could then:

  1. Interpret the user's question using the ontology.
  2. Determine which underlying sources are required.
  3. Generate SQL or another appropriate query.
  4. Retrieve the data from the original systems.

### 17. When graph storage can make sense

The discussion identified cases where actually putting data into a graph can be useful:

* Highly connected data.
* Graph traversal.
* Pattern detection.
* Graph-specific analytics.
* Algorithms such as:

  * Clustering.
  * Centrality.
* Rather than moving everything, an organization can identify the **subset of data that benefits from graph processing** and put that portion into the graph.

The hosts mentioned upcoming sessions:

* They also mentioned the continuing developer service and opportunities for feedback.

### 19. Resources mentioned

The hosts recommended:

### 20. Overall message

The central technical message of the episode is:

**A useful GraphRAG system combines vector-based semantic retrieval with an explicit, well-modeled knowledge graph. An ontology provides the common schema that keeps structured and unstructured data consistent, while graph relationships allow retrieved information to be enriched with additional context. Different retrieval strategies—vector, vector + graph, and text-to-Cypher—can then be used depending on the question.**

# Broadcast 7: Mar 4 - Enhancing LLM Tool Calling with Ontologies (https://youtube.com/live/WOyb7XW7ppQ)

Here are the main points made in the episode, organized by topic:

### 1. What is LLM tool calling?

* **Tool calling** lets an LLM use externally defined functions/tools when it needs them.
* Tools can interact with:

  * Databases
  * APIs
  * Other software/services
  * The external environment
* The LLM receives a set of available tools and decides whether one is useful for answering a user's request.
* If appropriate, the LLM generates a tool invocation with the required inputs.
* The tool executes and returns information, which the LLM then uses to formulate the final response.
* **“Tool calling” and “function calling”** are largely synonymous terms; LangChain uses “tool calling.”

### 2. Tool calling vs. RAG

* RAG generally works by retrieving relevant information and putting it into the LLM's context.
* Tool calling instead gives the LLM **functions it can invoke dynamically**.
* With vector-based RAG, the underlying documents are often relatively static or slow-changing.
* A tool can provide access to **live, transactional data**, such as:

  * A live database
  * Current weather through an API
  * Current stock information
* Neo4j can blur this distinction because it supports vector search while also being a live transactional database.

### 3. Basic tool-calling implementation

The demonstration uses:

* **LangChain**
* **OpenAI**
* **Neo4j**
* A Neo4j database containing data from the **Tate art collection**.

The graph contains information about:

* Artists
* Artworks
* Subjects/topics associated with artworks
* Relationships between subjects through a taxonomy

A simple tool was created:

* Input: an artist's name
* Operation: execute a Cypher query
* Output: artworks associated with that artist

For example:

> “List some works by William Blake.”

The LLM:

1. Determines that the `get_artist_works` tool is relevant.
2. Passes “William Blake” as the input.
3. The tool executes the Cypher query against Neo4j.
4. The returned artworks are given to the LLM.
5. The LLM produces a natural-language answer.

### 4. Tool descriptions are important

* A tool is more than just a function.
* Its **description is critical** because the LLM uses that description to decide when the tool should be invoked.
* Richer, clearer descriptions help the LLM choose between available tools.
* The LLM is generally responsible for deciding which tool to use in the demonstrated setup.

### 5. The problem with hard-coded tools

The initial implementation has an important limitation:

* Tool definitions and Cypher queries are written directly in application code.
* Adding or changing a tool requires changing the code.
* This makes the system less dynamic and less generic.

This motivates the central idea of the episode:

> **Move tool definitions into an ontology/graph rather than hard-coding them in application code.**

### 6. Using an ontology to define tools

The demonstration extends the graph's ontology with **tool definitions**.

The ontology already describes concepts such as:

* `Artwork`
* `Artist`
* `Subject`

Tool definitions are then associated with those concepts.

Each tool definition contains things such as:

* Tool name
* Description
* Cypher query
* Input information

For example:

* “Retrieve all artworks for a given artist.”
* “Retrieve the artists that most frequently use a particular subject.”

### 7. Dynamic tool generation

Instead of writing tools directly in Python/code:

1. The application queries the ontology.
2. It finds the tool definitions.
3. It reads their names, descriptions, queries, and parameters.
4. It dynamically creates the corresponding tools.
5. Those tools are registered with the LLM/agent.
6. The LLM can then choose among them.

So the architecture changes from:

**Code → Tools → LLM**

to something closer to:

**Ontology/Graph → Dynamic Tools → LLM**

### 8. Example: finding artists associated with a subject

A second dynamically defined tool was demonstrated.

The user asks something like:

> “Which artists use England as inspiration for their works?”

The tool:

* Finds artists
* Finds their artworks
* Finds subjects associated with those artworks
* Filters for the requested subject
* Counts the relevant artworks per artist
* Orders them by frequency
* Returns the top results

The LLM decides that this ontology-defined tool is appropriate and passes **“England”** as its parameter.

### 9. Adding tools without recompiling the application

One of the main benefits highlighted is that a new tool can be added by:

* Creating a new tool node/definition in the graph
* Providing its description
* Providing its Cypher query
* Providing its name

The application can then discover the new tool dynamically.

There is no need to:

* Modify the application code
* Hard-code another function
* Recompile/reconfigure the agent for every new tool

### 10. Separation of domain and database expertise

The approach also separates responsibilities.

For example:

* A **domain expert** can describe what capability is needed.
* A **database/Cypher expert** can implement the underlying query.
* The application dynamically exposes that capability to the LLM.

This can make the system more accessible to people who aren't experts in Cypher or the underlying database.

### 11. Traceability and provenance

Because the system knows which tool was used, it can potentially:

* Record which tool produced an answer.
* Attribute information to a particular source.
* Trace where particular pieces of information came from.
* Distinguish information retrieved from different databases or APIs.

This is useful for **answer provenance and explainability**.

### 12. Tools can evolve over time

The speakers suggest treating tools as evolving graph data.

You could track:

* How frequently each tool is used.
* Which tools are rarely or never used.
* Which tools produce problematic results.
* Which tools correlate with user dissatisfaction.
* Which tools should be refined or removed.

This creates the possibility of a **feedback loop for improving the tool ecosystem**.

### 13. Tools don't have to be read-only

A question from the audience raised whether tools can modify data.

The answer was **yes**.

Tools can potentially:

* Read data
* Write/update data
* Call APIs
* Trigger external actions

For example, an agent could theoretically use an API to make a travel booking.

However, the discussion suggests that **controlled/deterministic workflows** are particularly appropriate when tools can perform consequential actions.

### 14. Deterministic workflows vs. LLM-selected tools

There are two different approaches:

**LLM-driven approach**

* Give the LLM a collection of tools.
* Let it decide which tools to use and in what sequence.
* Flexible, but the exact execution path is delegated to the LLM.

**Deterministic workflow**

* Explicitly define the sequence and logic.
* Use something such as **LangGraph**.
* Better when the execution process needs to be controlled.

For example:

> Task A → Tool 1 → Tool 2 → Critic → Final result

rather than allowing the LLM to choose the entire workflow dynamically.

### 15. Semantic-layer analogy

An audience member compared the approach to a **semantic layer for SQL**.

The speakers agreed that there is an analogy:

* Both can capture domain meaning declaratively.
* Both can provide a conceptual layer over underlying data.
* Both can allow systems to use that semantic information dynamically.

But they distinguish their ontology approach from a traditional semantic layer, which may map relational tables to a more conceptual representation of the domain.

### 16. Shared/collaborative tool graph

The speakers also discussed the possibility of making the tool definitions collaborative.

A tool could potentially have metadata such as:

* Who created it
* Who is allowed to create/modify it
* Whether it requires approval
* Whether it has been reviewed
* Whether multiple people have contributed to it

They also suggested another architecture:

* Keep the ontology/tool definitions in one graph.
* Keep operational/business data in another graph.
* Query the ontology as a metadata/tool registry.

### 17. Automatically discovering tools from the ontology

A further “meta” idea was proposed:

Instead of humans manually creating all the tools, an LLM could:

1. Explore the graph schema/ontology.
2. Discover relationships between entities.
3. Identify potentially useful query patterns.
4. Generate candidate tools.

# Broadcast 8: Apr 8 - Agentic Workflows for Dynamic Ontology Selection in KG Construction (https://youtube.com/live/OhsfdRxcTqQ)

Here are the main points made in the transcript, organized by topic:

### 1. Topic and motivation

* The episode focuses on **“agentic workflows for dynamic/adaptive ontology selection in knowledge graph construction.”**
* It builds on earlier discussions about:

  * Knowledge graph construction from unstructured data.
  * Using ontologies to guide LLM-based entity extraction.
  * Agentic workflows.
  * Long-term/agentic memory.
* The central problem is: **What happens when incoming documents don't fit a single known ontology?**
* This is particularly relevant when users can upload arbitrary or unpredictable documents.

### 2. Problem with a fixed ontology

* A conventional GraphRAG pipeline works well when:

  * The document type/domain is known.
  * There is a predefined ontology for that domain.
* The problem is the **rigid mapping between incoming data and a particular ontology**.
* With thousands or millions of unstructured documents, it is unrealistic to know beforehand exactly what every document contains.
* Without an ontology/schema, completely unconstrained entity extraction can produce graphs that are difficult to query and use.
* Ontologies therefore act as **guardrails** that control and curate the resulting knowledge graph.

### 3. Proposed solution: dynamically select an ontology

The proposed workflow is:

1. Receive an unstructured document/text.
2. Perform a first-pass analysis to identify its key **categories/entities and relationships**.
3. Search a catalog of available ontologies using **semantic similarity**.
4. Calculate how much of the document is covered by the matching ontology.
5. If coverage is sufficient:

   * Select the ontology.
   * Pass it to the knowledge graph construction pipeline.
   * Build the graph using that ontology as a schema/guardrail.
6. If coverage is insufficient:

   * Generate a **candidate/new ontology**.
   * Present it for human validation.
   * Potentially refine, merge, validate, and eventually add it to the ontology catalog.
7. Future documents can then use the newly added ontology.

This creates an **adaptive ontology catalog** that can grow over time.

### 4. Why not give every ontology to the LLM?

* One possible solution would be to send the entire ontology catalog to the LLM and ask it to choose.
* This becomes problematic as the number of ontologies grows because:

  * The context becomes very large.
  * It becomes more expensive.
  * It adds unnecessary work for the LLM.
* The proposed approach instead **breaks the problem into stages**:

  * Extract broad concepts first.
  * Perform semantic search.
  * Select only relevant ontologies.

### 5. Ontology catalog

The demo creates a catalog containing three example ontologies:

* **Art ontology**

  * Artists
  * Artworks
  * Related properties and relationships
* **Books ontology**

  * Books
  * Authors
  * Genres
  * Reviews
  * Critics
* **Football ontology**

  * Football players
  * Football clubs
  * Cities
  * Relationships between them

The catalog could theoretically contain dozens, hundreds, or more ontologies.

### 6. Storing the ontology catalog in Neo4j

* The ontologies are stored in a separate **Neo4j database**.
* They are imported from Turtle/RDF files.
* Neo4j/Neo4j Semantics is used to load and represent the ontology structures.
* The ontology elements include classes, properties, relationships, labels, and descriptions.

### 7. Provenance

* The provenance points back to where the original ontology is hosted, in the demo's case GitHub.
* This maintains a connection between:

  * The ontology represented inside Neo4j.
  * The original ontology definition.
* In a real enterprise environment, the ontologies could remain completely private/internal.
* The speaker notes that using dereferenceable ontology URIs would be cleaner/better practice; the provenance property is mainly a simplified implementation for the demo.

### 8. Vectorizing the ontologies

To enable semantic ontology search:

* The labels, definitions, comments, properties, and relationships of ontology elements are converted into **embeddings**.
* These embeddings are stored in Neo4j.
* A **vector index** is created.
* This allows incoming concepts to be matched semantically rather than requiring exact terminology.

For example:

* Incoming term **“novel”** could match **“book.”**
* Incoming term **“athlete”** might potentially match **“football player.”**

* LangGraph represents the process as a directed graph of nodes and conditional branches.
* Each node performs a specific step.
* The workflow maintains a shared **state** across the steps.
* The state contains things such as:

  * Original input text.
  * Extracted categories/relationships.
  * Ontology matches.
  * Coverage information.
  * User validation response.

The key branching logic is essentially:

**Extract concepts → Find ontology → Is coverage sufficient?**

* **Yes → Build knowledge graph**
* **No → Propose candidate ontology**

### 10. Coverage threshold

# Broadcast 9: May 6 - Structural Patterns for Ontology Reconciliation (https://youtube.com/live/xuyJTHBbf0U)

Here are the main points made in the episode, organized by topic:

### 1. Episode topic and motivation

* The episode focuses on **structural patterns for ontology reconciliation**.
* The discussion returns to foundational topics: **semantics, ontologies, taxonomies, and knowledge graphs**, rather than focusing heavily on AI.
* Ontologies and AI/LLMs complement each other, but AI is intentionally kept mostly in the background for this session.
* The motivation came partly from a recent customer discussion about **reconciling different ontologies**.
* LLMs could eventually assist with ontology reconciliation, but the plan was to first explore **graph structure and structural matching**.

### 2. Why ontology reconciliation matters

* Ontologies can be represented as **graphs**, often containing taxonomic relationships such as `subclass of` or `type of`.
* They are not necessarily simple trees; a concept can have **multiple parents**.
* Structural features of these graphs can be used to identify **alignments and misalignments between different ontologies**.
* Ontologies are generally **human-curated expert knowledge**, so automatically detected alignments should often be treated as suggestions for human review rather than unquestionable results.
* Differences between ontologies may be meaningful—for example, one ontology may represent a concept with **two classes while another represents it with five**, indicating different levels of granularity.

### 3. RDFLib-Neo4j

* The demonstration uses **RDFLib-Neo4j**, a Neo4j Labs project.
* It is presented as a more client-oriented evolution of **Neo4j Semantics**.
* Neo4j Semantics traditionally worked as a server-side plugin extending Cypher functionality.
* RDFLib-Neo4j provides similar capabilities from the **Python/client side**, which is useful for environments such as Neo4j Aura.
* RDFLib is widely used for **RDF manipulation in Python**.
* RDFLib-Neo4j lets developers work with RDF graphs through RDFLib while having changes persisted into Neo4j.
* The basic setup is:

  1. Install the Python package.
  2. Create an RDFLib store backed by Neo4j.
  3. Parse/import RDF data.
  4. Neo4j handles the underlying property-graph representation.

### 4. RDF-to-Neo4j mapping

* RDF represents information as **triples: subject–predicate–object**.
* Neo4j uses **nodes, relationships, labels, and properties**.
* When RDF triples are imported:

  * Triples with the same subject are aggregated into the corresponding Neo4j resource/node.
  * Literal values become properties.
  * Connections between RDF resources become relationships.
  * URIs are preserved as unique identifiers.
* Much of this conversion happens transparently through RDFLib-Neo4j.
* A uniqueness index on resources is used so that the same URI does not result in duplicate resources.

### 5. Ontologies used in the demonstration

Three sources are used:

* **Wikidata**
* **MeSH (Medical Subject Headings)**
* **Disease Ontology**

The examples focus on **diseases and life sciences**, partly because life sciences has a particularly rich collection of public ontologies.

The speakers also mention:

* OBO Foundry as an important life-sciences ontology resource.
* Public ontology catalogs can be relatively scattered across industries.
* They invite viewers to suggest other useful ontology collections.

### 6. Extracting Wikidata data

* Wikidata provides a **SPARQL endpoint**.
* A SPARQL `CONSTRUCT` query is used to extract RDF rather than simply returning a table.
* The query starts from **infectious disease** and traverses subclass relationships.
* The `*` path operator allows traversal through an arbitrary number of subclass relationships.
* Information extracted includes:

  * Disease label/name
  * Description
  * Parent relationship
  * MeSH cross-reference
  * Disease Ontology cross-reference
* Labels and descriptions can be multilingual; the example uses English.
* The query constructs RDF triples in a custom namespace.
* Because the result is already RDF, it can be passed directly to RDFLib without creating a separate data model.

### 7. Importing Wikidata into Neo4j

* RDFLib connects to the SPARQL endpoint and executes the query.
* The resulting triples are stored in an RDFLib graph.
* That extracted graph is then parsed into the Neo4j-backed RDFLib store.
* Thousands of triples can be imported quickly.
* Once imported, the ontology can be visualized and queried as a Neo4j graph.
* The original URIs remain available, allowing users to navigate back to the corresponding Wikidata resources.

### 8. Removing redundant/inferred relationships

One important structural-cleaning technique is demonstrated.

Suppose the graph contains:

`A → parent → B → parent → C`

and also directly:

`A → parent → C`

The direct `A → C` relationship is **redundant**, because it can be inferred from the two existing parent relationships.

* Such relationships can add noise to the graph.
* They can be removed rather than permanently stored.
* The demonstration identifies and deletes these redundant relationships.
* This cleaned the example graph by removing **43 inferred/redundant relationships**.

### 9. Importing MeSH

* MeSH is accessed through its own **SPARQL endpoint**.
* The demonstration uses a slightly different ingestion approach:

  * An HTTP request is made to the SPARQL endpoint.
  * The result is returned in Turtle/RDF format.
  * The RDF output is passed into RDFLib-Neo4j.
* The actual ingestion into Neo4j remains essentially the same despite the different way the RDF was retrieved.
* MeSH concepts begin appearing in the same graph alongside Wikidata concepts.
* Existing `same as`/cross-reference relationships allow concepts from the different sources to be connected.

### 10. Importing Disease Ontology

Disease Ontology is obtained differently:

* Its releases are available through **GitHub** rather than through a SPARQL endpoint.
* The ontology is downloaded and parsed locally with RDFLib.
* RDFLib can then query the locally loaded graph using SPARQL.
* The resulting subset is imported into Neo4j.
* This demonstrates a third ingestion pattern:

  1. Query a SPARQL endpoint through RDFLib.
  2. Query a SPARQL endpoint through HTTP.
  3. Load an RDF dump locally and query it in memory.

Despite the different sources, the **Neo4j ingestion process is largely identical**.

### 11. Three structural patterns for reconciliation

#### A. Perfect/complete triangle

A strong alignment occurs when all three ontologies are connected.

Conceptually:

`Ontology A ↔ Ontology B ↔ Ontology C ↔ Ontology A`

* The three concepts form a triangle of cross-references.
* This gives strong evidence of an unambiguous correspondence.
* The demonstration finds examples where the names also match.

#### B. Incomplete triangle

* Two ontologies may be connected, while the expected third connection is missing.
* This creates an **incomplete triangle**.
* Such patterns can be used to identify potential missing mappings.
* The missing relationship could potentially be suggested for human validation.

#### C. Granularity mismatch

* Two ontologies may agree at the top and bottom but differ in the middle.
* For example:

`A ↔ B`

with an intermediate concept existing in one ontology but not the other.

* This indicates different **levels of granularity**.
* One ontology may model a domain more finely than another.
* The structural pattern helps identify this difference automatically.
* Whether the more detailed ontology should be used to extend the less detailed one is an **expert interpretation**, not something the graph can decide automatically.

### 12. Using descriptions and LLMs for future matching

* Structural relationships are only one source of evidence.
* Ontology classes often have textual **definitions/descriptions**.
* These descriptions could be converted into vectors and compared using **vector search**.
* LLMs could potentially provide another mechanism for identifying likely matches.
* This would be particularly useful for concepts that do **not already have explicit cross-references**.
* The intended approach could combine:

  * Structural patterns
  * Existing cross-references
  * Textual descriptions
  * Vector similarity
  * Potentially LLM-based analysis

### 13. Bringing multiple ontologies into one knowledge graph

The broader workflow is:

**External ontologies → RDF → RDFLib-Neo4j → Neo4j knowledge graph → structural analysis → ontology alignment**

Once multiple ontologies are in one graph:

* Their structures can be compared.
* Cross-references can be explored.
* Missing links can be identified.
* Granularity differences can be detected.
* Redundant relationships can be removed.
* Potential mappings can be surfaced for experts.

### 14. Connecting the reconciled ontology to internal data

The ultimate goal isn't necessarily just reconciling public ontologies.

The reconciled ontology can become a semantic layer for an organization's own data:

* Internal entities can be mapped to validated ontology concepts.
* Internal documents can be annotated with ontology terms.
* Internal data can be connected to external/global knowledge.
* Users can query relationships between internal and external concepts.
* This can support richer **knowledge graphs and semantic search**.

### 15. Ontologies for document annotation

* Ontologies are often used to annotate scientific papers and other sources.
* For example, a mention of a disease can be associated with a precise ontology concept.
* This enables **semantic search** and helps connect information across documents and datasets.
* Reconciliation can therefore improve consistency when different teams or organizations use different ontologies to annotate similar information.

### 16. Two different reconciliation use cases

The speakers identify two broad ways ontology reconciliation can create value:

1. **Reconciling the ontologies themselves**

   * Different organizations may have modeled the same domain differently.
   * Structural analysis can expose their similarities and differences.

2. **Making annotated data interoperable**

   * Mapping those ontologies can make the underlying data easier to combine and search.

### 17. RDF doesn't necessarily need to be user-facing

In response to a question about avoiding RDF:

* Users don't necessarily need to manually write or understand RDF.
* Ontology-building tools can provide graphical/user-friendly interfaces.

The central idea of the episode is:

### 3. Foundations of GraphRAG

* A major early theme was the difference between **vectors and graphs** for representing semantics.
* **Vector embeddings** capture semantic similarity implicitly.
* **Knowledge graphs** capture relationships and semantics explicitly.
* The two approaches are considered **complementary rather than competing**.
* Graphs provide advantages such as:

  * Explainability
  * Explicit relationships
  * Exploration/navigation
  * Richer context
* Vector search is relatively easy to implement and is effective for semantic similarity.
* However, vector similarity alone does not explain **why** two pieces of information are considered similar.
* Combining vector search with graph traversal can therefore improve retrieval and LLM responses.

### 4. Graphs Improve RAG Retrieval

* A basic GraphRAG pattern is:

  1. Perform vector search.
  2. Find relevant nodes.
  3. Traverse the surrounding graph.
  4. Use the additional context to improve the answer.
* Graphs can help with:

  * Contextualization
  * Re-ranking
  * Filtering
  * Moving from **similarity to actual relevance**
* Explicit relationships can also connect different chunks of a document.
* This prevents the system from considering relevant chunks in isolation and can produce more complete answers.

### 5. Ontology-Guided Retrieval

* The hosts explored using **ontologies to determine how graph traversal should happen**.
* Instead of blindly traversing a fixed number of hops, the system can use semantic information to decide what relationships are relevant.
* For example, if the retrieved item is a product, the system might explore categories, customers, purchases, etc.
* Ontologies can therefore make retrieval more **context-aware and dynamic**.

### 6. Different Retrieval Techniques

* One episode compared multiple retrieval approaches available in Neo4j.
* Techniques discussed included:

  * Vector search
  * Full-text search
  * Geospatial search
  * Graph traversal
  * Dynamically generated Cypher
* The key point was that different questions may require different retrieval strategies.
* Neo4j provides multiple retrieval mechanisms that can be combined depending on the use case.

### 7. Agentic AI & Tool Orchestration

* The discussion moved from one-shot RAG toward **agentic workflows**.
* Instead of hard-coding one retrieval strategy, multiple retrieval methods can be exposed as tools.
* An LLM can decide which tool or combination of tools to use based on the question.
* The hosts described an approach where an **ontology itself is used to represent available tools**.
* This allows new tools to be added dynamically without necessarily changing or redeploying the application code.
* They viewed this as an early example of what is now commonly called **agentic AI**.

### 8. LLMs as Assistants for Domain Modeling

The vector index can then search both kinds of entities.

* Subject → `text`
* Artist → `artistName`
* Artwork → `title`

These are effectively treated like identifiers/keys for the demo.

The ontology also identifies certain relationships as **contextualizing relationships**.

For example:

* Artist → artworks
* Subject → artworks

This tells the agent which relationships it should follow when it needs more context.

### 14. The important concept: ontology-driven behavior

This is the central point of the whole episode.

Instead of hard-coding rules such as:

> “If the result is an artist, find that artist's artworks.”

the agent asks the ontology:

> “What kind of thing is this, how is it identified, and which relationships should I follow to contextualize it?”

This makes the agent more **generic and adaptable**.

### 15. Three tools created for the agent

The agent uses three main tools.

#### Tool 1: Initial semantic search

* Takes the user's interest.
* Performs vector similarity search.
* Returns the most semantically similar graph entities.
* The demo limits the results to the top three.
* It can potentially return different types of entities, such as artists or subjects.

#### Tool 2: Ontology query for identifying properties

* Takes the type/label of a returned graph entity.
* Queries the ontology.
* Determines which property identifies that type.

For example:

```text
Artist → artistName
Subject → text
```

This allows the agent to determine dynamically how to retrieve a specific entity.

#### Tool 3: Contextualization

* Takes information about the returned entity.
* Uses the ontology to discover which relationships are marked as contextualizing.
* Traverses those relationships.
* Returns additional graph information.

For example:

```text
Artist
  ↓ createdBy / related relationship
Artwork
```

or

```text
Subject
  ↓ contextualizing relationship
Artwork
```

### 16. Tool descriptions matter

A significant point is that **tool descriptions influence agent behavior**.

The agent looks at:

* The overall prompt.
* The available tools.
* The descriptions of those tools.

It then decides which tools to use and in what sequence.

Therefore, clear and sufficiently detailed tool descriptions make it easier for the agent to select the correct tool.

### 17. Agent workflow

The intended workflow is:

```text
User interests
      ↓
Semantic/vector search
      ↓
Identify what each result is
      ↓
Query ontology
      ↓
Find identifying property
      ↓
Query ontology for contextualizing relationships
      ↓
Traverse graph
      ↓
Retrieve contextual information
      ↓
Generate personalized recommendation
```

### 18. Example test

They test the agent with interests such as:

* Andy Warhol
* Geometric shapes

They intentionally misspell Warhol as **“Warhole”** to demonstrate that semantic search does not require exact spelling.

The search successfully finds relevant results, including Andy Warhol.

### 19. Limitation discovered during testing

The presenters notice that the agent combined multiple interests into one search despite the prompt saying it should perform separate searches.

As a result:

* Andy Warhol was found.
* Other semantically similar artists such as Picasso appeared.
* The **geometric shapes** interest was not properly represented in the initial results.

They note that this could potentially be improved by **fine-tuning the agent prompt**.

### 20. Ontology successfully identifies entities

After the semantic search, the agent asks the ontology how to identify each result.

For example:

```text
Artist → artistName
Subject → text
```

This demonstrates that the agent does not need to have these relationships hard-coded.

The ontology supplies the information dynamically.

### 21. Interesting discovery: Andy Warhol as both artist and subject

The graph contains Andy Warhol in two different roles:

* As an **Artist**
* As a **Subject**

They discover an artwork depicting Andy Warhol by another artist.

This demonstrates why determining the entity type through the ontology is important: the same concept/name can have different meanings depending on its graph role.

### 22. Contextualization works differently by entity type

If the result is:

```text
Andy Warhol → Artist
```

the agent follows the ontology-defined contextualizing relationship to find **artworks created by Andy Warhol**.

If the result is:

```text
Andy Warhol → Subject
```

the agent follows the appropriate relationship to find **artworks depicting Andy Warhol**.

So the same textual concept can lead to different graph traversals depending on its type.

### 23. Embeddings are removed from final results

The presenters deliberately remove the `embedding` property before returning results to the language model.

Reason:

* Embeddings are large and aren't useful for text generation.
* Returning them would make the response unnecessarily large.
* Only useful graph information needs to be sent to the LLM.

### 24. Grounding and explainability

One of the major benefits demonstrated is **control and explainability**.

The agent's reasoning is grounded in:

* The vector search.
* The graph.
* The ontology.
* Explicit graph relationships.

Rather than letting an LLM freely invent a path through the data, the ontology helps control how information is retrieved.

### 25. The agent is generic

The agent itself doesn't need to contain all the specific graph-navigation rules.

Instead, those rules are represented in the ontology.

This means the same agent can potentially work with different ontology-driven structures without rewriting its fundamental logic.

### 26. Changing the ontology can change agent behavior

This is presented as one of the most powerful ideas.

If you change which relationships are marked as **contextualizing relationships**, you can change how the agent retrieves information.

For example, you could decide whether the agent should:

* Follow artist → artwork.
* Follow subject → artwork.
* Navigate the subject taxonomy.
* Explore additional relationships.

You can therefore **modify agent behavior by modifying ontology metadata rather than changing the agent itself**.

### 30. Overall takeaway

The main technical takeaway is:

> **Combine vector search for flexible discovery, a knowledge graph for structured context, and an ontology for controlling how an agent interprets and navigates that graph.**

The architecture separates the responsibilities:

```text
Vector search → Find potentially relevant things
Ontology → Understand what those things are and how to identify/contextualize them
Knowledge graph → Retrieve structured, connected information
LLM agent → Decide how to use the tools and generate the final response
```

The key advantage is that **the agent can remain generic while the ontology controls domain-specific behavior**, providing better structure, control, grounding, and explainability.

# Broadcast 3: Dec 9 - Ontologies, LLMs, Property Graphs - Do we really have a "Jaguar Problem"? (https://youtube.com/live/TJI6XiHSYt4)

Here are the main points made in the discussion, organized by topic:

### Core topic: the “Jaguar Problem”

* The **Jaguar Problem** refers to ambiguity in natural language: “jaguar” can mean an animal, a car, or a guitar model.
* The original argument being discussed was that **LLMs need an ontology to resolve this ambiguity and correctly construct a knowledge graph**.
* The presenters agree that ontologies are useful, but challenge several claims about what they guarantee when combined with LLMs.

### 1. LLMs can handle lexical ambiguity

* Claim challenged: **“LLMs cannot deal with lexical ambiguity without an ontology.”**
* The presenters argue that LLMs are actually very good at recognizing that “Jaguar” has multiple meanings.
* Even older LLMs can identify the animal, automobile, and guitar interpretations from context.
* An ontology can provide additional domain context, but it is **not necessary merely to recognize the ambiguity**.
* For example, an LLM can recognize that “I was hit by a Jaguar” could refer to a car, while a wildlife-related context points toward the animal.

### 2. An ontology in the prompt does not guarantee schema alignment

* Claim challenged: **“If you put an ontology into the LLM's context window, the generated data will conform to the ontology.”**
* An LLM treats the ontology as **textual guidance**, not as a deterministic symbolic schema.
* Example from the Jaguar dataset:

  * The ontology defines `occurs in` as a relationship between an **animal** and a **location**.
  * The LLM nevertheless produces a statement saying a **jaguar population** occurs in Sonora.
  * A population is not necessarily an individual animal.
* If an OWL reasoner subsequently processes this data, the ontology's domain definition could cause the system to infer that the population is an animal.
* This can lead to incorrect downstream results, such as counting populations as individual animals.
* Therefore, **putting an OWL ontology in an LLM prompt does not enforce the ontology's semantics**.

### 3. Ontologies don't eliminate the need for post-processing

* Claim challenged: **“The extracted triples require zero post-processing.”**
* The presenters argue that LLM-generated knowledge graphs still need:

  * validation,
  * quality checks,
  * consistency checks,
  * deduplication where appropriate,
  * and potentially additional processing.
* In the example:

  * Some entities have `rdfs:label` values while others don't, despite the prompt requesting labels.
  * Duplicate triples appear.
  * Some entities are interpreted questionably—for example, a group of students is classified as a `Person`.
* These behaviors demonstrate the **stochastic nature of LLMs**.
* An ontology provides guidance but does not act as an automatic guardrail around the LLM.
* A validation framework such as **SHACL** can be used after generation to check whether the resulting RDF satisfies specified constraints.

### 4. An LLM is not an OWL reasoning engine

* Claim challenged: **“The LLM can perform OWL reasoning/formal semantics.”**
* OWL reasoning is fundamentally different from language generation.
* A conventional OWL reasoner:

  * understands the formal semantics of OWL,
  * applies deterministic rules,
  * derives additional triples,
  * and can provide an explicit reasoning chain.
* An LLM does not provide those same guarantees.
* Even if an LLM sometimes produces the expected inferred result, that does not mean it is executing formal OWL reasoning.
* Complex reasoning involving things such as transitive or inverse-functional properties should therefore be delegated to an appropriate **symbolic reasoning engine**.

### 5. Natural-language descriptions may work better than OWL/RDF for LLM prompting

* Claim challenged: **“LLMs perform better when given an RDF/OWL ontology than when given an equivalent natural-language description.”**
* They conducted an experiment comparing:

  1. prompting an LLM with the OWL/Turtle ontology;
  2. prompting the same LLM with a natural-language description of the same ontology/domain.
* The same underlying Jaguar text was used.
* They ran the tests multiple times because LLM output is stochastic.
* They created a collection of **12 SPARQL-based evaluation queries** to measure extraction quality.
* The tests checked things such as:

  * whether all 16 Jaguars were extracted,
  * whether their names were captured,
  * whether particular properties were extracted,
  * whether observations were captured,
  * whether regions were connected correctly,
  * whether relationships such as parent/offspring were represented correctly.

### Experimental result

* In their reported experiment:

  * **Natural-language guidance passed about 62% of the tests.**
  * **OWL guidance passed about 53% of the tests.**
* Natural-language prompting therefore performed better in this particular experiment.
* The presenters emphasize that these are experimental statistics, not a universal law.
* Results can vary because LLMs are stochastic.
* Their broader explanation is that **LLMs are primarily trained on natural language**, so a natural-language description may sometimes be easier for them to use than a formal RDF/OWL representation.

### 6. OWL/RDF and property graphs are not mutually exclusive

* Claim challenged: **“This cannot be done with LPG/property graph databases.”**
* The presenters strongly reject the idea that ontologies require RDF/triple stores as their storage mechanism.
* An ontology is a **formal, machine-readable description of a domain**.
* It does not inherently dictate:

  * where data must be stored,
  * how data must be persisted,
  * or whether the resulting knowledge graph must use RDF storage.
* Ontologies can be used alongside **property graphs/LPGs**.
* RDF can also be transformed or imported into a property-graph representation.
* Property graphs are primarily a **data storage/management model**, whereas an ontology is a **knowledge/domain model**.
* These are different concerns and don't need to be placed in opposition.

### How the presenters suggest using ontologies with LLMs

The proposed workflow is roughly:

**Ontology → translate/derive a structured model → LLM extraction → structured output → validation → graph storage**

In particular:

* Keep the ontology as the authoritative formal representation.
* Parse the ontology programmatically.
* Translate it into something such as a **Pydantic model**.
* Use the Pydantic model with an LLM's **structured-output capabilities**.
* This can constrain the format and structure of the LLM's output much more reliably.
* If RDF is desired, the structured JSON can subsequently be represented as **JSON-LD/RDF**.
* The resulting data can then be stored in a property graph if that is the desired storage system.

### Important distinction: ontology vs. LLM

A recurring theme is the boundary between the two:

**Ontology**

* Formal
* Machine-readable
* Explicit semantics
* Deterministic when processed by appropriate reasoning/validation systems
* Can be parsed and transformed programmatically
* Can drive validation, inference, data models, and ingestion processes

**LLM**

* Language-based
* Probabilistic/stochastic
* Interprets its input rather than formally executing it
* Can ignore instructions
* Can hallucinate
* Does not guarantee formal semantic compliance

### Hallucinations remain possible

* Even when an ontology is supplied, hallucinations can occur.
* An example is a `dependent on` relationship between two Jaguar communities.
* The presenters say that relationship was **not supported by the source text**.
* They also point out that the geographic distance between the locations makes the claimed relationship questionable.
* Thus, adding an ontology does **not automatically eliminate hallucinations**.

### What ontologies *are* useful for

The presenters are not arguing against ontologies. Quite the opposite:

* They repeatedly say that **ontologies should be used** where appropriate.
* Their argument is about using them correctly.
* Ontologies can:

  * provide a shared vocabulary,
  * formally describe a domain,
  * support reasoning,
  * support validation,
  * drive data-ingestion pipelines,
  * be converted into application-specific models,
  * and work with both RDF and property graphs.

### Overall takeaways

1. **LLMs can resolve lexical ambiguity**, so an ontology isn't required simply to understand that “Jaguar” has multiple meanings.
2. **Putting an ontology into an LLM prompt doesn't guarantee semantic/schema compliance.**
3. **LLM-generated triples need validation/post-processing.**
4. **LLMs should not be treated as OWL reasoning engines.**
5. **Natural-language descriptions can sometimes outperform formal OWL/RDF prompts for LLM extraction.**
6. **Ontologies and property graphs are compatible**, rather than mutually exclusive.
7. **Structured outputs/Pydantic models can provide stronger output constraints** than simply putting an OWL ontology into the prompt.
8. **Hallucinations remain possible even with an ontology.**
9. The ontology can remain the **formal master representation**, while being transformed into models or schemas appropriate for LLM-based ingestion.
10. The key is to understand **what the ontology guarantees and what the LLM does not guarantee**.

### The closing perspective

The speakers ultimately frame the discussion as a clarification rather than an argument against the original author's work. The original author explains that his goal was to demonstrate how **RDF, OWL, and LLMs could generate interest in knowledge graphs**, rather than to establish all of the stronger claims attributed to the example. He acknowledges that, knowing the post would receive more attention, he would have made the example more rigorous and nuanced.

The final message is essentially: **use ontologies, use LLMs, and use property graphs where appropriate—but don't confuse a formal ontology/reasoner with an LLM interpreting text.**
