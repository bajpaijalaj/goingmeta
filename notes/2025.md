# Broadcast 5: Jan 7 (https://youtube.com/live/0c3WicsmLuo)

Here are the main points made in the episode, organized by topic:

### 1. Episode focus: combining structured and unstructured data

* The episode focuses on **knowledge graph construction from mixed data**.
* “Mixed data” means combining:

  * **Structured data** — CSV files, relational databases, tables, etc.
  * **Unstructured data** — PDFs, free-text documents, product descriptions, credit notes, etc.
* The central idea is to use **one common ontology** to drive the construction of the knowledge graph from both types of data.
* This reflects an enterprise reality where information is spread across many different sources but needs to be represented using a common domain model.

### 2. Ontology as the common model

* An ontology is described as a **formal, machine-readable representation of a domain**.
* It can range from a simple schema containing:

  * Entities/classes
  * Relationships
  * Properties/attributes
* More sophisticated ontologies can also contain:

  * Taxonomies
  * Constraints
  * Actions
  * Other semantic information
* The ontology acts as the **target model or blueprint** for the knowledge graph.
* Using a common ontology helps maintain:

  * Consistency
  * Alignment
  * Reusability
  * Interoperability

### 3. Different representations of an ontology

* Ontologies can be represented using **W3C standards**, such as:

  * OWL
  * RDFS
  * RDF vocabularies
* The ontology doesn't have to originate in a particular tool.
* A machine-readable ontology can be transformed into other representations and models.
* The episode demonstrates converting a W3C ontology into a **graph model that can be imported into Neo4j Aura's model catalog**.
* Conversely, a graph model created in Neo4j can be converted back into an RDF/W3C representation.

### 4. Neo4j Aura Graph Model / Model Catalog

* Neo4j Aura has a **Graph Models / Model Catalog** capability.
* A graph model can be created manually by defining:

  * Nodes/entities
  * Relationships
  * Properties
* The model can then be saved in the catalog and used to drive data ingestion.
* More importantly, the model can be **generated from an existing ontology**, avoiding the need to recreate the model manually.
* This allows an existing industry or enterprise ontology to become the basis for a Neo4j knowledge graph.

### 5. Reusing existing/public ontologies

* The presenters emphasize that organizations should **reuse existing ontologies where possible rather than reinventing them**.
* Examples shown include:

  * An insurance ontology
  * A building/construction ontology
* Public ontologies can provide a starting point for modeling a domain.
* An imported ontology can also be **extended or modified** to accommodate an organization's specific requirements.
* Using an established ontology can help with interoperability because the resulting graph follows an existing standard.

### 6. Ontology → Neo4j graph model

The demonstrated workflow is roughly:

**W3C ontology → parse ontology → select relevant classes → generate JSON graph model → import into Neo4j Aura → use model for data ingestion**

* The demo application takes an ontology URL.
* It scans the ontology and identifies its classes and properties.
* Users can select which classes they actually need.
* The application generates a JSON representation of the selected model.
* That model is imported into the Neo4j Aura Graph Model catalog.
* The resulting model contains the ontology's entities, relationships and properties.

### 7. Example: sales ontology

The main demonstration uses a **sales domain**.

The ontology contains concepts such as:

* Product
* Customer
* Purchase
* Location
* Credit Note
* Store

Relationships include concepts such as:

* Purchase → customer
* Purchase → product
* Credit Note → purchase
* Customer → location

Properties include things such as:

* Customer ID
* Customer name
* Email
* Product code
* Product name
* Purchase date
* Quantity
* Credit note date
* Refund amount

### 8. Structured data ingestion

The structured data consists of several CSV files, including:

* Customers
* Purchases
* Locations

The Neo4j data importer is used to map the CSV fields to the ontology/model.

For example:

* `customer_id` → Customer ID
* `full_name` → Customer name
* `email` → Customer email
* Purchase ID → Purchase identifier
* Quantity → Purchase quantity
* Product ID → Product identifier

Foreign keys in the relational data are used to establish relationships between the graph entities.

### 9. The structured data is incomplete

* An important point in the demo is that the structured data doesn't contain all the information needed by the ontology.
* For example, the purchase data contains only limited information about products.
* Additional product information exists in **unstructured PDF documents**.
* Similarly, credit-note information isn't present in the structured CRM data.
* Therefore, the graph needs to be assembled from multiple sources.

### 10. Using GraphRAG for unstructured data

* The presenters then use the **Neo4j GraphRAG Python package** and its Knowledge Graph Builder pipeline.
* The pipeline processes PDFs by:

  1. Loading documents
  2. Parsing them
  3. Splitting them into chunks
  4. Creating embeddings
  5. Extracting entities
  6. Extracting relationships
  7. Writing the resulting information into the knowledge graph

### 11. Two graphs are produced from the unstructured data

The GraphRAG process creates two conceptual layers:

**Lexical/document graph**

* Documents
* Chunks
* Text
* Embeddings
* Relationships between documents and chunks

This supports retrieval approaches such as vector search.

**Domain/knowledge graph**

* Extracted entities
* Relationships between entities
* Domain-specific properties

The domain graph is the more important part for the ontology-driven knowledge graph.

### 12. The ontology provides the GraphRAG guardrails

This is one of the central technical points.

Instead of letting an LLM freely decide what entities and relationships to extract, the ontology supplies:

* Allowed entities
* Allowed relationships
* Properties
* Potential connections between entities

The GraphRAG pipeline therefore uses the ontology as a **schema/guardrail for extraction**.

Conceptually:

**Ontology → extraction schema → LLM extraction → knowledge graph**

This makes the generated graph more controlled and aligned with the intended domain model.

### 13. Combining structured + unstructured data

After both ingestion processes are complete:

* Structured CRM data exists in the graph.
* Unstructured PDFs have contributed additional entities and relationships.
* Because both were constructed according to the **same ontology**, they can connect naturally.

For example:

**Credit Note → Purchase → Customer → Location**

Some of the information in that chain comes from the PDFs, while other information comes from the CRM/CSV data.

The ontology provides the common structure that allows the two sources to connect.

### 14. Why this approach is useful

The presenters highlight several benefits:

* A single model can govern multiple data sources.
* Data from different systems can be brought together consistently.
* Less reliance on unconstrained LLM-generated schemas.
* Greater consistency and potentially fewer extraction/modeling errors.
* Easier interoperability with other systems.
* Ability to reuse established industry standards.
* Easier modeling when you don't know how to design the graph from scratch.

### 15. Ontologies don't have to be complete

* An imported ontology should be treated as a **starting point**, not necessarily a finished model.
* An organization may:

  1. Find an existing ontology.
  2. Import it.
  3. Keep the relevant parts.
  4. Add its own concepts and relationships.
* This lets organizations benefit from existing standards while adapting them to their own domain.

### 16. Finding existing ontologies

A question is raised about pre-existing ontologies for areas such as:

* Expense management
* Procurement
* Life sciences
* Pharma
* Construction

The response is that repositories and catalogs exist, but finding suitable ontologies can still require significant research.

Important considerations when selecting one include:

* How recently it has been updated
* How widely it is used
* Whether it is actively maintained
* Whether other projects use it
* How well it matches the intended domain

### 17. Multiple ontologies can potentially be combined

* The discussion notes that multiple ontologies can be imported and their relevant portions combined into a graph model.
* For example, one ontology could provide a people/customer concept while another provides product concepts.
* Only the portions relevant to the particular application need to be retained.

### 18. Why convert the ontology to JSON?

A question asks why the ontology isn't simply imported directly in Turtle/RDF format.

The explanation is that the demonstrated intermediate JSON step allows the process to:

* Parse the ontology.
* Select only relevant classes.
* Select the required portion of the model.
* Generate a Neo4j-compatible graph model.

The RDF/Turtle representation remains the standard ontology serialization; JSON is simply part of the demonstrated import workflow.

### 19. Ontology vs. Pydantic constraints

A Q&A discussion distinguishes **ontology modeling** from **validation constraints**.

* Ontologies primarily describe the domain/schema:

  * Classes
  * Relationships
  * Properties
* They aren't necessarily equivalent to the detailed validation constraints you might define with Pydantic.
* For richer RDF-based constraints, the presenters mention **SHACL**.
* Examples of constraints include requirements such as:

  * A relationship must exist.
  * A relationship can occur a minimum/maximum number of times.
  * A property must follow a particular format.
* Therefore:

  * **Ontology ≈ domain/schema description**
  * **SHACL/Pydantic ≈ validation/constraints**

### 20. Ontologies can be modified inside Neo4j

* Once a graph model is imported into Neo4j, it can be modified.
* Elements can be:

  * Added
  * Removed
  * Extended
* The important architectural question is then deciding which representation is the **master/source of truth**.
* An organization needs to establish an ontology lifecycle and versioning strategy.

### 21. Closing the circle

The episode demonstrates that the workflow can work in both directions:

**Ontology → Neo4j model → graph**

and

**Neo4j model → RDF/W3C ontology representation**

Therefore, the starting point doesn't necessarily have to be an external ontology.

You could:

* Start with a formal ontology.
* Start with a Neo4j graph model.
* Transform between representations.
* Use the resulting model to drive data ingestion.

### 22. Ontologies and reasoning

The final Q&A touches on:

* Decision-rule engines
* Solvers
* Forward chaining
* Backward chaining
* Inferencing

The presenters point out that ontologies can also be used for **reasoning/inference**, beyond simply providing a schema.

They refer viewers to an earlier episode on **“Reasoning 101”** for this topic.

### 23. SQL databases → ontologies

Another question asks about tools for going from SQL databases to ontologies.

The discussion distinguishes between:

* Creating an ontology from a relational schema.
* Mapping an existing relational database to an existing ontology.

They mention an earlier approach using an LLM to derive an ontology/schema from a relational database and note that other ontology/data-mapping tools also exist.

### 24. Overall workflow demonstrated

The whole episode can essentially be reduced to this:

**Existing ontology**
↓
**Convert/import it into a Neo4j graph model**
↓
**Use the model to map structured data**
↓
**Use the same ontology as the extraction schema for unstructured data**
↓
**Build the knowledge graph**
↓
**Automatically connect information from both sources**
↓
**Query the combined graph**

### 25. Main takeaway

The core message of the episode is:

> **Create or reuse an ontology once, then use that common model to control both structured-data ingestion and LLM-based extraction from unstructured data.**

This provides a more consistent way to construct a knowledge graph from enterprise data that comes in many different forms.

# Broadcast 6: Feb 4 (https://youtube.com/live/0c3WicsmLuo](https://youtube.com/live/GPmHpp3QEWc)

Here are the main points made in the transcript, organized by topic:

### 1. Episode purpose

* This episode is a **Q&A and feedback session** rather than a completely new topic.
* The hosts wanted to:

  * Recap the previous episode.
  * Explain the parts that were covered too quickly.
  * Answer questions collected from the community.
  * Take live questions from viewers.
* Viewers watching later were encouraged to leave questions in the YouTube comments, Discord, or community forums.

### 2. Recap: Knowledge Graph + RAG

* Previous episodes focused on:

  * Knowledge graph construction.
  * Knowledge Graph Builder.
  * GraphRAG.
  * Combining structured and unstructured data.
* The central concept is an **ontology/domain schema** that acts as a common model for different data pipelines.
* The example used a sales dataset containing:

  * Customers.
  * Purchases/orders.
  * Products.
  * Locations.
  * Credit notes/refunds.
* Structured data came from a CRM.
* Unstructured data came from PDFs such as:

  * Product descriptions.
  * Credit/refund notes.
* The same ontology was used to guide both structured-data ingestion and unstructured-data extraction.

### 3. Why the ontology matters

* Without guidance, an automatic knowledge graph can produce a graph that is difficult to use.
* The ontology provides **guardrails/scaffolding** by defining:

  * Entity types.
  * Relationships.
  * Labels.
  * Properties.
  * Terminology.
  * Unique identifiers.
* This helps different data-ingestion pipelines create a **consistent, unified graph**.
* The ontology can be created first and then converted into the formats required by different tools.
* Alternatively, the schema can be defined directly in code.

### 4. What GraphRAG adds to ordinary vector RAG

* Ordinary vector RAG:

  * Converts text into embeddings.
  * Searches for similar vectors.
  * Returns the most similar chunks to an LLM.
* The limitation is that similarity alone may return information that is relevant but incomplete.
* GraphRAG combines:

  * Vector search.
  * Explicit entities.
  * Relationships.
  * Structured data.
  * Graph traversal.
* This allows retrieved information to be **contextualized by navigating the graph**.
* GraphRAG can therefore support multiple retrieval patterns, including:

  * Vector search.
  * Vector search + graph traversal.
  * Text-to-Cypher.
* Sometimes the vector index can even be bypassed and a structured query can be generated directly.

### 5. The two-layer graph

The demonstrated graph contains two complementary parts:

* A **lexical/vector layer**:

  * Documents are split into chunks.
  * Chunks contain text.
  * Text is converted into embeddings.
  * Embeddings are stored in a vector index.
* A **domain/entity layer**:

  * Entities such as products, customers, purchases, and credit notes are extracted.
  * These entities are connected through relationships.

This means a document chunk can be connected to a real product, customer, order, etc.

### 6. Combining CRM data with unstructured documents

* CRM data contained relatively limited product information, such as product IDs.
* Product-description documents contained much richer information:

  * Product specifications.
  * Features.
  * Details.
  * Other descriptive text.
* Credit notes contained information such as:

  * Credit-note ID.
  * Date.
  * Customer.
  * Address.
  * Purchase/order reference.
  * Refund amount.
  * Refund reason.
* Credit notes could therefore be linked to customers, products, and purchases.

### 7. Entity resolution problem

* Data from different sources does not always use identical identifiers.
* Example:

  * One source used a product identifier like `catcore_000459`.
  * Another source used only `459`.
* Because the identifiers weren't exactly identical, automatic merging didn't occur.
* The hosts demonstrated a small Cypher transformation to:

  * Remove the prefix.
  * Remove leading zeros.
  * Convert the value into a comparable representation.
* Once the identifiers matched, the two product nodes could be merged.

### 8. APOC and merging nodes

* APOC was used to simplify graph operations.
* `mergeNodes` can combine two or more nodes into one.
* It can also control how:

  * Properties are handled.
  * Relationships are handled.
  * The merge takes place.
* APOC provides many utility procedures/functions that would otherwise require more Cypher code.
* The hosts noted the distinction between **APOC Core and APOC Extended**, because some functions are available only in Extended.

### 9. Result: connected structured + unstructured graph

After resolving the product IDs:

* Structured data and unstructured data became connected.
* A possible path could go from:

  * Product description → product → purchase → credit note
  * Or between other combinations of structured and unstructured entities.
* This creates a graph through which an application can navigate between information from different sources.

### 10. Three retrieval approaches demonstrated

#### A. Vector Retriever

* The simplest approach.
* The question is converted into an embedding.
* The vector index is searched.
* The top-N similar chunks are returned.
* The LLM generates an answer from those chunks.
* Example question:

  * “What do you know about smart watches?”
* The approach worked well for relatively straightforward questions about product descriptions.

#### B. Vector + Cypher Retriever

* Starts with vector search.
* The resulting nodes are then used as starting points for graph traversal.
* Additional structured information can be retrieved from connected nodes.
* Example:

  * Find a product from its description.
  * Traverse to purchases.
  * Count sales.
  * Traverse to credit notes.
  * Count returns.
* This can answer richer questions such as customer satisfaction around a product.
* Example result:

  * A portable charger had a sales count of 130 and four returns.
* A limitation is that the Cypher retrieval query is **hardcoded**.
* The hosts suggested that future agentic RAG approaches could expose multiple retrieval tools and let the LLM decide which one to use.

#### C. Text-to-Cypher Retriever

* Instead of searching a vector index, the system asks an LLM to generate a Cypher query.
* The LLM needs the database schema/ontology as context.
* The process is:

  1. User asks a natural-language question.
  2. The ontology/schema is provided to the LLM.
  3. The LLM generates Cypher.
  4. The Cypher query is executed.
  5. The result is returned.
* Example:

  * “How many orders have been returned for products with AI functionality in their features?”
* The generated Cypher identified products, purchases, credit notes, and the relevant product features, then counted the matching results.
* The example returned **five**.
* There can be variability in how the LLM interprets terms such as “AI functionality,” so generated queries may not always behave identically.

### 11. Controlling what information reaches the LLM

* A **result formatter** can determine what information retrieved by Cypher is passed to the LLM.
* It can include:

  * Node properties.
  * Relationship information.
  * Properties of neighboring nodes.
  * Paths.
  * Aggregated values.
  * Metadata.
* This provides control over how much context is sent to the generation step.

### 12. Controlling the number of vector matches

* For vector retrieval, the application can specify the number of top results to return.
* For example:

  * Top 2.
  * Top 3.
  * Top 5.
* Vector indexes can use similarity measures such as:

  * Euclidean distance.
  * Cosine similarity.
* There isn't inherently a priority between a node's value and its other properties during vector search; the indexed/vectorized property is what is searched.
* Additional filtering can be performed afterward using Cypher.

### 13. LLM choice

* The demonstration used OpenAI models, mainly for demonstration purposes.
* The hosts emphasized that GraphRAG isn't restricted to OpenAI.
* Other supported options can be used, including:

  * Azure-hosted models.
  * Local models such as those run through Ollama.
* The choice of embedding and generation model is configurable.

### 14. GraphRAG vs LangChain

* A viewer asked about LangChain's Neo4j graph Q&A functionality.
* The answer was that **both approaches are valid**.
* LangChain may be preferable for developers already familiar with its APIs.
* The Neo4j GraphRAG package provides another way of implementing the same general retrieval concepts.
* The Neo4j team is working toward better organization and ongoing maintenance of the integration.

### 15. Comparing RAG approaches

* Performance shouldn't simply be judged from one or two examples.
* A proper evaluation requires a collection of questions and expected answers.
* The hosts compared this conceptually to **unit testing**.
* Useful evaluation frameworks include **RAGAS**.
* Evaluation can consider things such as:

  * Whether the answer contains the expected information.
  * Whether it contains unnecessary noise.
  * Whether retrieval is relevant.
* Quantifying the benefit of a RAG architecture is important when justifying its cost to customers.

### 16. When to move from a relational database to a graph

* The hosts explicitly said there is **no universal answer**.
* They would not recommend automatically moving all relational data into a graph.
* One option is to leave the original data where it is and use a graph as a **semantic layer**.
* The semantic layer can describe:

  * Entities.
  * Ontology.
  * Relationships.
  * Where data is stored in underlying systems.
* For example, the graph could say that customer information comes from a particular relational table or document collection.
* A retrieval system could then:

  1. Interpret the user's question using the ontology.
  2. Determine which underlying sources are required.
  3. Generate SQL or another appropriate query.
  4. Retrieve the data from the original systems.

### 17. When graph storage can make sense

The discussion identified cases where actually putting data into a graph can be useful:

* Highly connected data.
* Graph traversal.
* Pattern detection.
* Graph-specific analytics.
* Algorithms such as:

  * Clustering.
  * Centrality.
* Rather than moving everything, an organization can identify the **subset of data that benefits from graph processing** and put that portion into the graph.

# Broadcast 6: Mar 4 (https://youtube.com/live/WOyb7XW7ppQ)

Here are the main points made in the episode, organized by topic:

### 1. What is LLM tool calling?

* **Tool calling** lets an LLM use externally defined functions/tools when it needs them.
* Tools can interact with:

  * Databases
  * APIs
  * Other software/services
  * The external environment
* The LLM receives a set of available tools and decides whether one is useful for answering a user's request.
* If appropriate, the LLM generates a tool invocation with the required inputs.
* The tool executes and returns information, which the LLM then uses to formulate the final response.
* **“Tool calling” and “function calling”** are largely synonymous terms; LangChain uses “tool calling.”

### 2. Tool calling vs. RAG

* RAG generally works by retrieving relevant information and putting it into the LLM's context.
* Tool calling instead gives the LLM **functions it can invoke dynamically**.
* With vector-based RAG, the underlying documents are often relatively static or slow-changing.
* A tool can provide access to **live, transactional data**, such as:

  * A live database
  * Current weather through an API
  * Current stock information
* Neo4j can blur this distinction because it supports vector search while also being a live transactional database.

### 3. Basic tool-calling implementation

The demonstration uses:

* **LangChain**
* **OpenAI**
* **Neo4j**
* A Neo4j database containing data from the **Tate art collection**.

The graph contains information about:

* Artists
* Artworks
* Subjects/topics associated with artworks
* Relationships between subjects through a taxonomy

A simple tool was created:

* Input: an artist's name
* Operation: execute a Cypher query
* Output: artworks associated with that artist

For example:

> “List some works by William Blake.”

The LLM:

1. Determines that the `get_artist_works` tool is relevant.
2. Passes “William Blake” as the input.
3. The tool executes the Cypher query against Neo4j.
4. The returned artworks are given to the LLM.
5. The LLM produces a natural-language answer.

### 4. Tool descriptions are important

* A tool is more than just a function.
* Its **description is critical** because the LLM uses that description to decide when the tool should be invoked.
* Richer, clearer descriptions help the LLM choose between available tools.
* The LLM is generally responsible for deciding which tool to use in the demonstrated setup.

### 5. The problem with hard-coded tools

The initial implementation has an important limitation:

* Tool definitions and Cypher queries are written directly in application code.
* Adding or changing a tool requires changing the code.
* This makes the system less dynamic and less generic.

This motivates the central idea of the episode:

> **Move tool definitions into an ontology/graph rather than hard-coding them in application code.**

### 6. Using an ontology to define tools

The demonstration extends the graph's ontology with **tool definitions**.

The ontology already describes concepts such as:

* `Artwork`
* `Artist`
* `Subject`

Tool definitions are then associated with those concepts.

Each tool definition contains things such as:

* Tool name
* Description
* Cypher query
* Input information

For example:

* “Retrieve all artworks for a given artist.”
* “Retrieve the artists that most frequently use a particular subject.”

### 7. Dynamic tool generation

Instead of writing tools directly in Python/code:

1. The application queries the ontology.
2. It finds the tool definitions.
3. It reads their names, descriptions, queries, and parameters.
4. It dynamically creates the corresponding tools.
5. Those tools are registered with the LLM/agent.
6. The LLM can then choose among them.

So the architecture changes from:

**Code → Tools → LLM**

to something closer to:

**Ontology/Graph → Dynamic Tools → LLM**

### 8. Example: finding artists associated with a subject

A second dynamically defined tool was demonstrated.

The user asks something like:

> “Which artists use England as inspiration for their works?”

The tool:

* Finds artists
* Finds their artworks
* Finds subjects associated with those artworks
* Filters for the requested subject
* Counts the relevant artworks per artist
* Orders them by frequency
* Returns the top results

The LLM decides that this ontology-defined tool is appropriate and passes **“England”** as its parameter.

### 9. Adding tools without recompiling the application

One of the main benefits highlighted is that a new tool can be added by:

* Creating a new tool node/definition in the graph
* Providing its description
* Providing its Cypher query
* Providing its name

The application can then discover the new tool dynamically.

There is no need to:

* Modify the application code
* Hard-code another function
* Recompile/reconfigure the agent for every new tool

### 10. Separation of domain and database expertise

The approach also separates responsibilities.

For example:

* A **domain expert** can describe what capability is needed.
* A **database/Cypher expert** can implement the underlying query.
* The application dynamically exposes that capability to the LLM.

This can make the system more accessible to people who aren't experts in Cypher or the underlying database.

### 11. Traceability and provenance

Because the system knows which tool was used, it can potentially:

* Record which tool produced an answer.
* Attribute information to a particular source.
* Trace where particular pieces of information came from.
* Distinguish information retrieved from different databases or APIs.

This is useful for **answer provenance and explainability**.

### 12. Tools can evolve over time

The speakers suggest treating tools as evolving graph data.

You could track:

* How frequently each tool is used.
* Which tools are rarely or never used.
* Which tools produce problematic results.
* Which tools correlate with user dissatisfaction.
* Which tools should be refined or removed.

This creates the possibility of a **feedback loop for improving the tool ecosystem**.

### 13. Tools don't have to be read-only

A question from the audience raised whether tools can modify data.

The answer was **yes**.

Tools can potentially:

* Read data
* Write/update data
* Call APIs
* Trigger external actions

For example, an agent could theoretically use an API to make a travel booking.

However, the discussion suggests that **controlled/deterministic workflows** are particularly appropriate when tools can perform consequential actions.

### 14. Deterministic workflows vs. LLM-selected tools

There are two different approaches:

**LLM-driven approach**

* Give the LLM a collection of tools.
* Let it decide which tools to use and in what sequence.
* Flexible, but the exact execution path is delegated to the LLM.

**Deterministic workflow**

* Explicitly define the sequence and logic.
* Use something such as **LangGraph**.
* Better when the execution process needs to be controlled.

For example:

> Task A → Tool 1 → Tool 2 → Critic → Final result

rather than allowing the LLM to choose the entire workflow dynamically.

### 15. Semantic-layer analogy

An audience member compared the approach to a **semantic layer for SQL**.

The speakers agreed that there is an analogy:

* Both can capture domain meaning declaratively.
* Both can provide a conceptual layer over underlying data.
* Both can allow systems to use that semantic information dynamically.

But they distinguish their ontology approach from a traditional semantic layer, which may map relational tables to a more conceptual representation of the domain.

### 16. Shared/collaborative tool graph

The speakers also discussed the possibility of making the tool definitions collaborative.

A tool could potentially have metadata such as:

* Who created it
* Who is allowed to create/modify it
* Whether it requires approval
* Whether it has been reviewed
* Whether multiple people have contributed to it

They also suggested another architecture:

* Keep the ontology/tool definitions in one graph.
* Keep operational/business data in another graph.
* Query the ontology as a metadata/tool registry.

### 17. Automatically discovering tools from the ontology

A further “meta” idea was proposed:

Instead of humans manually creating all the tools, an LLM could:

1. Explore the graph schema/ontology.
2. Discover relationships between entities.
3. Identify potentially useful query patterns.
4. Generate candidate tools.
5. Have humans curate/approve those tools.

So the system could potentially become a **self-discovering tool-generation system**, with humans remaining in the curation loop.

### 18. Overall architectural idea

The central takeaway is:

> **Use the ontology/knowledge graph not only to store data, but also to store metadata describing how that data can be accessed and used.**

This moves more of the application's logic into the graph.

Instead of having application code contain:

* Domain knowledge
* Query definitions
* Tool definitions
* Tool descriptions

much of that information can be represented declaratively in the ontology/graph.

### 19. Claimed benefits

The speakers identify several potential benefits:

* More dynamic tool calling
* Less hard-coded application logic
* Easier addition of new capabilities
* Better separation of domain and technical expertise
* More generic application code
* Potentially easier maintenance
* Tool usage tracking
* Source/provenance tracking
* Ability to evolve tools over time
* Possibility of collaborative tool management
* Potential for human-curated automatically generated tools
* Ability to combine databases and APIs behind different tools

### 20. Final conceptual point

The episode connects this idea to a broader philosophy they've used with RAG:

> **Move as much of the logic and domain knowledge as practical into the data/knowledge layer, making the application itself more generic and dynamic.**

The ontology therefore becomes more than a description of **what exists in the domain**. It can also describe **what the system can do with that domain**.
