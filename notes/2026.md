# Broadcast 4: Jan 6 - Evaluating the Quality of Ontologies (https://youtube.com/live/16oBgsWPX1o)

Here are the main points made in the episode, organized by topic:

### 1. Episode and event introduction

* The episode is **Going Meta, Season 3, Episode 4**, starting the 2026 series.
* The hosts discuss returning from the holiday/New Year break.
* **NODES AI** is highlighted as an upcoming major event in April 2026.
* A **Road to NODES workshop series** is planned for March.
* The submission deadline for NODES has passed, but exceptional late contributions may still potentially be accommodated if submitted quickly.
* Attendees are encouraged to register for NODES.

### 2. Why ontology quality evaluation matters

* Ontologies have been used throughout previous episodes, but the focus has generally been on **using ontologies**, not on systematically evaluating how good they are.
* The episode focuses on **methods and metrics for measuring ontology quality**.
* The hosts emphasize that ontology construction and evaluation are inherently iterative:

  1. Build an ontology.
  2. Evaluate it.
  3. Improve it.
  4. Evaluate it again.
* There is no single universal quality metric; **the appropriate metrics depend on the ontology's purpose and desired outcome**.
* The episode draws on existing academic literature rather than proposing an entirely new evaluation methodology.

### 3. Two broad types of ontologies

The hosts distinguish two practical categories:

#### A. Domain ontologies

* Describe a particular domain or area of interest.
* Act as an **enriched semantic schema** for a knowledge graph.
* Define entities/classes, properties, and relationships.
* Can be mapped to structured data such as:

  * Tables
  * CSV files
  * Source systems
* Can also guide **entity extraction from unstructured data**.
* Can drive knowledge-graph retrieval.
* Usually have fewer entities than large taxonomies but richer relationships.
* These are the primary focus of the episode.

#### B. Large taxonomies

* Can contain thousands or even millions of concepts/classes.
* Primarily provide **hierarchical organization**.
* Usually have less relational richness than domain ontologies.
* Often used to **annotate external sources**.
* Examples discussed include terminology systems from life sciences, such as disease/medical vocabularies.
* The distinction is a practical classification based on how the hosts see ontologies being used, rather than a universal academic classification.

### 4. Four major ontology-quality evaluation areas

The episode identifies four broad categories:

1. **Structural metrics**
2. **Requirement/coverage metrics**
3. **Pragmatic/usability metrics**
4. **Logical soundness**

The hosts stress that these categories can be combined according to the particular project.

---

## 5. Structural metrics

Structural evaluation looks at the internal structure of an ontology.

Questions include:

* How many relationships does each class have?
* How many ancestors does a class have?
* Are classes connected?
* Are there orphan classes?
* Are there cycles or unwanted loops?
* How strongly are classes connected?
* What is the overall shape of the ontology?

### Class Connectivity Coverage

One metric discussed is **Class Connectivity Coverage**.

The basic idea is:

> What fraction of the ontology's classes are connected to other classes through relationships?

Conceptually:

**Connected classes / Total classes**

The hosts demonstrate this using:

* An OWL movie ontology.
* RDFLib/RDFLib-Neo4j.
* Neo4j Aura.
* Cypher queries.

They import the ontology into Neo4j and calculate the metric programmatically.

### Extended connectivity

Two variants are demonstrated:

* **Connected count** — considers direct incoming/outgoing relationships.
* **Connected count extended** — also considers relationships inherited through the class hierarchy.

The point is that the exact implementation of a metric may vary depending on what the evaluator considers "connected."

---

## 6. Property richness

Another structural metric is **property richness**.

The basic concept is to examine the relationship between:

* Properties associated with an ontology/class.
* Relationships connecting classes.

The hosts note that a global property-richness number can hide useful information.

Therefore, they demonstrate a **class-centric variant**, where property richness is calculated separately for each class.

For example:

* A class may have zero locally defined properties.
* It may nevertheless participate in several relationships.
* Properties may actually be inherited from a parent class.

This illustrates an important principle:

> Metrics should not necessarily be followed literally; they should be adapted to the meaning and needs of the particular ontology.

Other structural metrics mentioned include:

* **Lack of cohesion**
* **Coupling between objects (CBO)**
* Variants that consider:

  * Taxonomic relationships only.
  * Taxonomic + domain/range relationships.
  * Inherited relationships.

---

## 7. Don't blindly follow metrics

A major message is that ontology-quality metrics are **guidelines rather than rigid rules**.

* Academic papers may define metrics differently.
* Some metrics have multiple possible implementations.
* Some metrics may be useful in one context but less useful in another.
* Existing research can provide inspiration for designing project-specific metrics.
* Teams should understand **what a metric actually measures** before using it.

---

## 8. Build an ontology-quality dashboard

The hosts demonstrate putting the metrics into a **Neo4j dashboard**.

The dashboard can show:

* Class connectivity.
* Extended connectivity.
* Property richness.
* Other structural metrics.
* Annotation coverage.

Benefits:

* Gives a single view of ontology quality.
* Makes gaps visible.
* Allows metrics to be monitored while developing the ontology.
* Can potentially be extended with multiple pages/tabs and interactive elements.

A snapshot dashboard shows the current state. To track evolution over time, the ontology would need to be **versioned**, with metrics recorded for each version.

---

## 9. Pragmatic/usability metrics

The next category asks:

> How easy is the ontology for people and systems to use?

One important metric is **annotation coverage**.

Questions include:

* Does each class have a human-readable label?
* Does it have a description/comment?
* Is the ontology documented?
* Is it understandable?

The demonstration calculates:

* Total classes.
* Annotated classes.
* Percentage of classes with annotations.

The hosts note that this could be split into separate metrics, such as:

* Label coverage.
* Description/comment coverage.

### Why this matters

An ontology can technically work but still be difficult to use if:

* Classes are poorly described.
* URIs aren't understandable.
* Documentation is missing.

The goal is to make the ontology **usable, discoverable, and understandable**.

---

## 10. Referenceability

Another pragmatic metric is **referenceability**.

An ideal ontology should:

* Be publicly or organizationally accessible.
* Be discoverable.
* Have reachable definitions.
* Allow each ontology element to be dereferenced.
* Return meaningful information when someone accesses its identifier/IRI.

One possible implementation is:

1. Perform an HTTP GET request against an ontology IRI.
2. Check whether meaningful information is returned.

This was discussed but not implemented during the session.

---

## 11. Competency-question coverage

This is one of the more interesting evaluation approaches.

The ontology should be created to answer specific **competency questions**.

A competency question is essentially:

> What question must the ontology/knowledge graph be able to answer?

For example:

* Who lived at a particular address?
* What was their artistic activity?
* Can we retrieve all parents of a person?
* Can we infer that someone's mother is also a person?

The evaluation asks:

> Does the ontology contain enough concepts, properties, and relationships to answer these questions?

This connects ontology quality directly to the **requirements the ontology was built to satisfy**.

---

## 12. Using LLMs to evaluate competency-question coverage

The hosts demonstrate using an LLM as an ontology QA assistant.

The LLM receives:

* An OWL ontology represented as text.
* A list of competency questions.

It evaluates each question using scores such as:

* **1** — the ontology clearly supports answering it.
* **0.5** — it partially supports it.
* **0** — it does not support it.

The LLM can additionally provide:

* Explanations.
* Missing concepts/properties.
* Suggestions for improving the ontology.
* Example Cypher queries.

An example ontology produced an overall coverage score of **0.25**, with some individual questions fully supported and others only partially or not supported.

The hosts emphasize that an LLM is **not a formal inference engine** here. It is being used to inspect the ontology and assess how well it appears to cover the questions.

---

## 13. Logical soundness

The fourth category is **logical consistency**.

Ontologies can contain formal logical statements such as:

* Domain/range restrictions.
* Subclass relationships.
* Disjoint classes.
* Property constraints.
* Other OWL constructs.

These can accidentally introduce contradictions.

### Example with koalas

The hosts demonstrate this using Protégé and a reasoner.

The ontology says, in effect:

* A koala is a marsupial.
* A particular property implies something about being a person.
* A koala is therefore indirectly inferred to be a person.
* But the ontology also says **persons and marsupials are disjoint**.

This creates an inconsistency:

* Koala → Marsupial
* Koala → Person
* Person ∩ Marsupial = empty

A reasoner can detect this and identify the problematic/unsatisfiable class.

### Key takeaway

If an ontology uses advanced OWL constructs and logical restrictions, use a **reasoning engine** to detect inconsistencies.

---

## 14. Keep ontologies simple

Alex makes an important practical point:

* Don't make an ontology unnecessarily complicated.
* It's easy to start with a simple model and gradually add excessive complexity.
* Avoid adding classes, relationships, loops, or structures simply because they seem theoretically appropriate.
* Step back periodically and ask whether the complexity is actually necessary.
* A good model should contain what is needed while avoiding unnecessary complexity and dead ends.

## 15. Make ontology quality measurable

One of the strongest themes of the episode is:

> **Don't rely only on intuition; instrument the ontology-development process.**

Instead of saying:

* "This ontology looks good."
* "This change seems better."

Use measurable metrics.

For example:

* Run 20 competency questions.
* Track how many pass/fail.
* Measure annotation coverage.
* Measure connectivity.
* Measure property richness.
* Run logical consistency checks.

Then compare those measurements between ontology versions.

This makes it possible to detect:

* Quality improvements.
* Quality degradation.
* Gaps introduced by changes.

---

## 16. Integrate evaluation into the ontology lifecycle

The metrics shouldn't just be run once at the end.

The proposed process is:

**Build → Measure → Modify → Measure → Compare → Repeat**

Whenever the ontology changes:

* Re-run the metrics.
* Record the results.
* Compare them against previous versions.
* Use the results to guide further development.

This turns ontology quality evaluation into an ongoing part of the **ontology lifecycle**.

The hosts agree that this is a common and useful approach.

Important sources for ontology construction can include:

A generic ontology may provide a starting point, but it often needs to be **adapted to the specific problem being solved**.

## 19. Ontology marketplaces and reuse

The hosts discuss the idea of having a broader ecosystem/marketplace of reusable:

* Ontologies.
* Knowledge-graph concepts.

More published and reusable ontologies could:

* Make it easier for others to get started.

## 20. Overall framework

The episode ultimately presents ontology quality as a combination of four perspectives:

| Area                     | Main question                                                  |
| ------------------------ | -------------------------------------------------------------- |
| **Structural**           | Is the ontology structurally well connected and organized?     |
| **Requirement/Coverage** | Does it cover the questions and requirements it was built for? |
| **Pragmatic/Usability**  | Is it documented, accessible, discoverable, and usable?        |
| **Logical soundness**    | Does its formal logic contain inconsistencies?                 |

### Core message

The overall philosophy is to **combine the metrics that make sense for your particular ontology**, automate them where possible, put them into a dashboard/pipeline, and track them as the ontology evolves.

The episode is therefore less about declaring that there is a single "quality score" for an ontology and more about creating a **repeatable, measurable quality-evaluation process**.

# Broadcast 5: Feb 3 - Neo4j Agent Memory (https://youtube.com/live/rnERHmj81VI)

Here are the main points made in the session, organized by topic:

### 1. Agent memory and decision tracing

* The goal is to build AI agents that can **learn from previous interactions and decisions**, rather than responding only to the current prompt.
* Useful memory should capture:

  * What happened
  * Why it happened
  * The reasoning and steps taken
  * Risk factors and exceptions
  * Previous decisions or precedents
* Decision traces can be reused to improve future agent executions.

### 2. Why use graphs for agent memory?

* The speakers argue that **graphs are a natural representation for agent memory** because they connect:

  * Conversations
  * Messages
  * Entities
  * Facts
  * Preferences
  * Agent actions
  * Reasoning steps
* Several companies are already building graph-based agent-memory products.
* The broader idea is sometimes described as a **context graph**, especially when the graph contains not only knowledge but also the context and reasoning surrounding an agent's actions.

### 3. Neo4j Agent Memory

* The session introduces **Neo4j Agent Memory**, a new Labs/open-source project.
* It provides an API for storing and retrieving three major kinds of memory:

  1. **Short-term memory**
  2. **Long-term memory**
  3. **Reasoning memory**
* These three types can be combined to create a richer context graph for an AI agent.

### 4. Short-term memory

Short-term memory represents the **current conversation/session**.

* It stores messages exchanged between the user and the assistant.
* Each conversation has a unique session ID.
* Messages are linked sequentially, forming a conversation chain.
* Messages are timestamped and embedded/vectorized.
* The graph can therefore support:

  * Deterministic retrieval of a conversation
  * Retrieval of messages in their original sequence
  * Semantic/vector search for similar messages
* Entity extraction can happen automatically as messages are stored.

**Example:**

* User: “I'm looking for a restaurant.”
* Assistant: “What's your favorite cuisine?”
* User: “I love Mediterranean cuisine.”
* The system stores the messages and automatically extracts “Mediterranean” as an entity.

### 5. Long-term memory

Long-term memory represents information extracted from conversations and stored as a more traditional **knowledge graph**.

It can contain:

* **Entities** — people, organizations, places, objects, etc.
* **Relationships** between entities
* **Preferences** — e.g. a user's food preferences
* **Facts**
* **Temporal validity** of facts — when a fact became valid and when it stopped being valid
* Potentially geospatial information

For example:

* Person: John Smith
* Preference: likes Italian food
* Fact: subject → predicate → object
* Fact → valid from → valid until

### 6. Automated entity extraction

* The memory package contains an entity-extraction pipeline.
* Entity extraction doesn't necessarily have to rely entirely on an LLM.
* It can use models such as:

  * spaCy
  * GLiNER
  * An LLM as a fallback
* A confidence threshold can determine when an LLM should be used because a smaller/local model isn't sufficiently confident.
* This can reduce:

  * Cost
  * Processing time
  * Privacy concerns
* Local models can process sensitive text without sending it outside the organization's network.
* Entity extraction can also support:

  * Deduplication/merging
  * Enrichment using external sources
  * Domain-specific entity types

### 7. Domain-specific entity extraction

* Different domains need different entity types.
* A general-purpose model might recognize people, objects, locations and events.
* A podcast-focused model, for example, could recognize:

  * Participants
  * Topics
  * Episodes
  * Other podcast-specific concepts
* Custom named-entity recognition models can be trained for specific domains.

### 8. Reasoning memory

Reasoning memory captures the **“why” and “how” behind an agent's actions**.

Instead of only recording:

> “The agent recommended restaurant X.”

it records the execution that led to the recommendation.

A reasoning trace can contain:

* The task being performed
* Individual reasoning/execution steps
* Tool calls
* Tool names
* Tool arguments
* Tool results
* Success/failure status
* Execution duration
* The final outcome
* A link back to the message that triggered the task

### 9. Example reasoning trace

For a restaurant recommendation:

1. User asks for a restaurant.
2. Agent starts a restaurant-recommendation trace.
3. Agent decides to search for nearby restaurants.
4. Agent calls a restaurant-search tool.
5. Query: Italian restaurants.
6. Tool returns two possible restaurants.
7. Tool call is marked successful.
8. Agent selects one restaurant.
9. Trace records the final recommendation.

All of these steps can be persisted as connected graph data.

### 10. Learning from previous traces

This is one of the major reasons for storing reasoning traces.

An agent can search for **similar previous executions**.

This allows the system to identify:

* Previously successful approaches
* Previously unsuccessful approaches
* Similar tasks
* Reusable execution patterns
* Potential opportunities to avoid repeating work

A successful previous execution could potentially act like a **cache or reusable procedure**, provided its result is still applicable.

An unsuccessful execution can provide a signal to **avoid repeating the same approach**.

### 11. Agent evaluation and hallucinations

The discussion highlights that reasoning traces can be useful for **evaluating agents**.

One important signal is tool-call status.

For example:

1. Agent decides it needs a transcript.
2. It calls a transcript-retrieval tool.
3. The tool fails.
4. Instead of recognizing the failure, the LLM generates an answer anyway.

The trace would expose this sequence and make it possible to identify that the agent's response was produced despite a failed tool call.

This makes tool-call lineage and success/failure information valuable for **observability and debugging**.

### 12. Turning repeated traces into tools

The speakers suggest another possible use for reasoning traces:

* Suppose an agent performs essentially the same task hundreds of times.
* Analysis of the traces could reveal a stable, successful sequence of steps.
* That repeated pattern might eventually be turned into:

  * A dedicated tool
  * A predefined workflow
  * A sub-agent
  * A procedure with explicit guardrails

So agent memory isn't only about remembering the past; it could help **discover and formalize reliable agent procedures**.

### 13. Trace analysis and observability

The package reportedly includes functionality for:

* Filtering traces
* Analyzing traces
* Observability
* Inspecting executions

The underlying idea is that storing the execution history makes agent behavior more transparent and traceable.

### 14. Conversation summaries

The system can also generate a summary of a conversation.

It can:

* Retrieve the conversation
* Retrieve extracted entities
* Pass the information to an LLM
* Produce a concise human-readable summary

Example result:

* The user is looking for a restaurant.
* The user prefers Mediterranean cuisine.

This combines short-term conversational information with extracted long-term information.

### 15. Memory inside a real assistant

The demo then shows memory integrated into an actual conversational assistant.

Example interaction:

* User provides their name.
* User says they love football.
* User says they support Real Madrid.
* User says they want to buy a football kit.
* User specifies that they're interested in an Italian club kit.

As the conversation progresses:

* Messages are stored.
* Entities are extracted.
* The graph grows.
* The assistant can later retrieve what it knows about the user.
* A “memory” operation can provide a summary of the information currently known.

The demo successfully shows short-term and long-term memory, although the presenter wasn't able to fully demonstrate procedural/reasoning memory in the integrated assistant example.

### 16. Context graph vs. knowledge graph

A significant discussion concerns where the boundary lies between a **knowledge graph** and a **context graph**.

The speakers argue that there isn't necessarily a clear boundary.

A traditional knowledge graph tends to focus on:

* **What is true**
* Entities
* Relationships
* Facts
* Sources/provenance

Agent/context memory can additionally capture:

* What happened
* When it happened
* Why something happened
* How an agent reached a decision
* What tools were used
* What context existed at the time
* What exceptions or reasoning occurred

Their view is essentially that these can all be interconnected rather than treated as completely separate graphs.

### 17. Provenance and explainability

Graph-based memory can improve **explainability**.

For example:

* An agent uses a fact to answer a question.
* The fact can be linked to the context in which it was used.
* The fact can also be linked back to its original document/source.
* The resulting chain provides an end-to-end explanation of where the information came from and how it contributed to the answer.

The graph therefore connects:
**source → fact → context → agent reasoning → answer**

### 18. Short-term → long-term memory

Another open question is when information should move from short-term memory into long-term/domain memory.

The example given is a learning assistant:

* A learner expresses frustration about a particular lesson.
* Initially, that is simply part of the current conversation.
* The system could decide to persist that feedback into the broader domain graph.
* Aggregated feedback could then help improve the course or learning experience for future users.

This illustrates that memory isn't necessarily just personal memory; it can potentially become **organizational/domain knowledge**.

### 19. Overall architecture

The session effectively presents a layered model:

**Short-term memory**
→ conversations and messages

**Long-term memory**
→ entities, relationships, preferences and facts

**Reasoning memory**
→ traces, steps, tools, decisions and outcomes

Together:
→ **richer agent context / context graph**

### 20. Main takeaway

The central idea of the session is that **AI-agent memory should capture more than conversation history**.

A useful memory system can preserve:

> **What the user said + what the system knows + what the agent did + why it did it + what happened as a result.**

Putting all of this into a connected graph makes it possible to retrieve past context, discover similar situations, evaluate agent behavior, improve future decisions, support explainability, and potentially turn successful recurring behaviors into reusable tools or workflows.


# Broadcast 6: Mar 3 - Validating Neo4j Graphs with SHACL (https://youtube.com/live/u7fsq5vEA3E)

Here are the main points made in the episode, organized by topic:

### 1. Episode topic

* The episode is about **validating Neo4j graphs using SHACL**.
* SHACL is revisited as part of the broader “Going Meta” discussion around graph semantics and property graphs.
* The goal is to show both the concepts and a practical implementation.

### 2. Why graph validation matters

* Graph validation is important for maintaining **data quality**.
* Validation can detect:

  * Incorrect graph structure.
  * Incorrect relationships.
  * Incorrect relationship cardinalities.
  * Incorrect node/relationship types.
  * Invalid property types.
  * Invalid property values.
* Instead of writing individual Cypher queries for every validation rule, the goal is to describe the rules **declaratively** and let software translate them into executable Cypher.

### 3. Data-quality rules vs. business rules

The same validation mechanism can cover both low-level data-quality constraints and higher-level business rules.

Examples mentioned:

* A customer's phone number must match a particular regular expression.
* A product must have at least a certain number of suppliers.
* A supplier must have exactly one name.
* An order may only contain properties from a predefined collection.
* A product having at least two suppliers can be viewed as a **business rule**, because it could represent supply-chain resiliency rather than simply data correctness.

The key idea is:

> Both data-quality and business rules can be represented as patterns that should or should not exist in the graph.

### 4. Neo4j's flexibility vs. validation

* Property graphs are intentionally flexible.
* For example, two `Person` nodes can have different sets of properties.
* This flexibility is useful during development because it allows rapid iteration.
* As a graph matures, organizations may want more **structure, consistency, and discipline**.
* SHACL can provide these “guard rails” without removing the flexibility of the underlying property graph.

### 5. What is SHACL?

* **SHACL (Shapes Constraint Language)** is a **W3C Recommendation/standard** for defining constraints on graphs.
* It provides a declarative way to describe what a graph should look like.
* SHACL defines the **what**, rather than the implementation-specific **how**.
* The validation system discussed in the episode translates those declarative constraints into something executable against Neo4j.

### 6. Anatomy of a SHACL shape

A SHACL shape can describe constraints for particular categories/types of nodes.

For example, a `Product` shape can specify:

* Which nodes the rules apply to.
* Required or permitted properties.
* Property data types.
* Regular-expression patterns.
* Minimum/maximum cardinality.
* Minimum/maximum values.
* Relationship types.
* Types of nodes at the other end of relationships.
* Relationship cardinality.

Example concepts from the demo:

* `productName` must match a particular pattern.
* `productName` can have at most one value.
* `productName` must be a string.
* `unitPrice` must have one value.
* `unitPrice` must fall within a specified range.
* A product's `supplies` relationships must connect to suppliers and satisfy a minimum cardinality.

### 7. SHACL doesn't have to be written manually

The speakers point out that users don't necessarily need to write raw RDF/SHACL syntax themselves.

Possible approaches include:

* Writing SHACL directly.
* Generating it using an LLM.
* Using a tool/library that generates SHACL.
* Using the **Graph Expectations** Python package.

### 8. Graph Expectations

* Graph Expectations provides a more **Pythonic way of defining graph constraints**.
* Instead of writing RDF-based SHACL syntax, users create Python objects describing their expectations.
* Those expectations can then be serialized into SHACL/RDF.
* SHACL remains the underlying formal representation.

The structure is roughly:

* **Set** → defines the nodes being constrained.
* **Expectations** → defines the constraints.
* **Suite** → groups multiple sets/expectations together.

### 9. Sets can be more expressive than labels

A constraint doesn't necessarily have to apply to every node with a particular label.

A set can be defined by:

* A node label/type, such as `Company` or `Customer`.
* A more complex expression/query.

For example:

* Apply a rule only to nodes located in a particular region.
* Apply a rule to a specific subset of customers, suppliers, or products.

This allows validation rules to target **specific subsets of a graph**.

### 10. Why the new approach is useful

Earlier implementations relied on **Neo4j Semantics** providing SHACL functionality.

The new approach:

* Runs on the **client side**.
* Does not require Neo4j Semantics.
* Therefore works with Neo4j deployments where Neo4j Semantics isn't available, including the discussed Aura scenario.
* Takes SHACL definitions and translates them into Cypher queries.

This demonstrates the broader idea that a declarative semantic definition can have multiple implementations.

### 11. Northwind example graph

The demo uses the **Northwind dataset** loaded into Neo4j Aura.

The graph contains concepts such as:

* Customers.
* Orders.
* Products.
* Suppliers.

Relationships represent things such as:

* Customers placing/purchasing orders.
* Orders containing products.
* Suppliers supplying products.

This graph is used as the test data for validation.

### 12. Creating validation rules with Graph Expectations

The demo creates expectations for `Supplier` nodes.

Examples include:

* A supplier's `country` property must match a regular expression.
* A supplier must not simultaneously be a customer.
* A supplier must have a certain number of outgoing relationships.
* Relationship types and cardinalities can be constrained.

Rules can also have:

* A descriptive name/message.
* A severity.
* An identifier/alias.

These identifiers make validation results easier to understand.

### 13. Product validation rules

The demo also creates rules for products.

Examples:

* `unitPrice` must have exactly one value.
* `unitPrice` must be unique.
* `unitPrice` must fall within a defined range, such as 10–500.
* Rules can be given names such as `price limit`.

Multiple sets of expectations can then be added to the same **suite**.

### 14. Version control and lifecycle

An important advantage of representing rules declaratively is that they become **software/data artifacts**.

The SHACL definitions can be:

* Serialized.
* Stored in GitHub.
* Version-controlled.
* Tracked over time.
* Incorporated into software-development workflows.
* Used as part of data-ingestion processes.
* Changed as the graph and business requirements evolve.

### 15. Running validation

The validation process consists broadly of:

1. Connect to the Neo4j database.
2. Create a validation client.
3. Import/parse the SHACL shapes.
4. Translate the shapes into executable Cypher.
5. Run the generated validation queries against the graph.
6. Produce a validation report.

The result includes an overall **conformance** status plus detailed violations.

### 16. Understanding validation violations

The demo shows that the graph initially **does not conform** to all the defined shapes.

The report identifies things such as:

* The type of constraint violated.
* The affected node.
* The affected property or relationship.
* The offending value.
* The rule that was violated.

For example:

* A product has a `unitPrice` of `6`.
* The rule requires the price to be between `10` and `500`.
* Therefore, that product is reported as violating the `price limit` rule.

### 17. Validation rules can be changed dynamically

The demonstration changes the price constraint:

* Initially: minimum price = 10.
* Later: minimum price = 5.

After reloading/recompiling the shapes and running validation again:

* Many violations disappear.
* Only products with prices below 5 remain as violations.

This illustrates the **declarative and dynamic** nature of the approach:

* Change the rule.
* Re-run validation.
* The underlying Cypher is regenerated automatically.

### 18. Inverse relationship paths

One particularly interesting SHACL capability demonstrated is the **inverse path**.

The rule is:

* A product must have at least two suppliers.

The `supplies` relationship is stored from the supplier toward the product, so when starting from a product, the relationship needs to be traversed **in reverse**.

SHACL can express this using an inverse path.

This is useful because the business requirement concerns the product:

* “Each product must have at least two suppliers.”

It would be awkward to express that rule from the supplier side because a supplier can supply many products.

### 19. Business-rule example: low product offering

The inverse relationship example is given a business-oriented interpretation:

* If a product has only one supplier, its supply offering is at risk.
* Therefore, requiring at least two suppliers can be treated as a business-monitoring rule rather than merely a data-quality rule.

The same validation framework can therefore be used for both.

### 20. Generated Cypher is transparent

The SHACL rules aren't magically executed.

Behind the scenes:

* SHACL is parsed.
* The validation client generates Cypher.
* Those Cypher statements identify violations.
* The queries are executed against Neo4j.

The system allows users to **inspect the generated Cypher**.

This is useful for:

* Understanding how the rules are implemented.
* Debugging.
* Verifying behavior.
* Running individual generated queries manually if desired.

### 21. Example of generated Cypher

For the `unitPrice` range rule, the generated Cypher:

* Finds product nodes.
* Retrieves their `unitPrice`.
* Handles possible null values.
* Handles potentially multi-valued properties.
* Checks whether values fall outside the allowed range.
* Reports violations.

The user doesn't need to write this Cypher themselves; it is generated from the declarative rule.

### 22. Validation can be restricted to part of the graph

The system doesn't always have to validate the entire graph.

For very large graphs, such as one with hundreds of millions of nodes, validation can be limited to:

* A particular set of nodes.
* A recently ingested batch.
* A specific subset of the graph.

For example:

* Instead of validating the entire graph, validate only nodes 5 and 6.

This can make incremental data-ingestion validation more practical.

### 23. Rules themselves are dynamic

The set of constraints can evolve over time.

Users can:

* Add rules.
* Remove rules.
* Modify existing rules.
* Track changes through version control.

The expectation is that the collection of shapes will evolve alongside the graph and its requirements.

### 24. Main takeaway

The overall workflow presented is:

**Define what the graph should look like → express those requirements as SHACL → optionally generate SHACL through Graph Expectations → translate SHACL into Cypher → run validation against Neo4j → receive detailed violation reports.**

The central message is that **graph validation can be declarative, reusable, version-controlled, dynamic, and independent of manually written Cypher validation queries**.

**Same database**

### 4. Google’s Open Knowledge Format (OKF)

* The discussion briefly covers Google's **Open Knowledge Format**.
* It is described as building on an emerging **"LLM Wiki" pattern**.
* The basic idea involves:

  * Markdown files representing concepts

  * Tags for grouping concepts
  * Links between concepts
  * A directory/file structure that AI agents can navigate

* The format is seen as a potentially flexible standard for allowing AI agents to navigate large collections of knowledge.
* The speakers suggest a possible future Neo4j integration/demo around this.

### 5. Topic of the episode: actionable knowledge for agents

The main topic is **"Actionable Knowledge for Agents with Context Graph."**

The discussion focuses on how agent memory can evolve from simply storing information into something that provides **reusable knowledge and procedures** to AI agents.

### 6. Three types of agent memory

Will describes three types of memory:

#### Short-term memory

* Represents the current conversation.
* Essentially a sequence of messages between the user and agent.

#### Long-term memory

* Contains entities and relationships extracted from conversations.
* These entities and connections form a knowledge graph.

#### Reasoning memory

* Stores how an agent actually solved a task.
* Can include:

  * Reasoning steps
  * Decisions
  * Tool calls
  * Execution paths
  * Token usage
  * Execution time
  * Observability information
* It is also related to what is sometimes called **procedural memory**.

### 7. Context Graph

* These different memory types can be connected into a **Context Graph**.
* The graph provides a common substrate for AI-agent context.
* Agents can retrieve relevant information from this graph while reasoning.

### 8. Why reasoning memory matters

The speakers highlight several benefits of recording an agent's decisions and actions:

* **Explainability** — understanding why a decision was made.
* **Auditability** — being able to trace decisions and actions.
* **Predictability/determinism** — agents can follow established approaches rather than inventing a new approach every time.
* **Reusability** — one agent can benefit from how another agent solved a similar problem.
* **Cost reduction** — agents can avoid repeatedly performing expensive reasoning.

A concrete example mentioned:

* A customer reportedly achieved approximately a **33% token reduction** after implementing a reasoning-memory/proxy approach in an example.

### 9. From memory to actionable knowledge

* Simply storing memories isn't enough.
* The next step is to **distill useful knowledge from the memory graph**.
* One way to do this is through **skills**.

### 10. What is an AI-agent "skill"?

* A skill is described as a portable package of instructions that an agent can use.
* It can contain:

  * A `skill.md` entry point
  * Instructions
  * Reference information
  * Scripts/code
  * Other supporting material
* Examples include skills for:

  * Creating PowerPoint presentations
  * Writing Neo4j Cypher
  * Data modeling
  * Other repeatable tasks

### 11. Modeling skills as graphs

* Normally, skills are largely represented as prose/Markdown.
* The Neo4j research team explored representing skills as **graphs instead**.
* The discussed research is called the **Agent Instruction Protocol (APE)**.
* The idea is to represent:

  * Steps
  * Dependencies
  * Scripts/tools
  * Relationships between steps
    as graph structures.

### 12. Why graph-based skills could help

A prose-based skill requires an agent to repeatedly:

* Read the instructions
* Interpret them
* Identify entities
* Figure out dependencies
* Determine what steps to execute

A graph-based representation can explicitly encode those relationships.

Potential advantages discussed:

* Greater determinism
* Better efficiency
* Better portability
* Easier maintenance
* Easier evolution over time
* Clearer dependencies between skill components

### 13. Skill benchmarking

* The research team tested the approach using the **SkillsBench benchmark**.
* They reported that graph-based APE skills achieved a statistically significant higher pass rate in their experiments.
* Some skills that failed in prose form had a greater chance of succeeding when represented using the APE format.

### 14. Skill distillation

Neo4j has applied these ideas to its agent-memory tooling through **skill distillation**.

The basic process is:

**Agent conversations → Memory graph → Reasoning traces/entities → Distilled skill**

* The system examines previous agent interactions.
* It identifies entities and reasoning information.
* It converts the useful patterns into a reusable skill.
* The resulting skill can then be reviewed and published.

### 15. Skills can be grounded in real data

* An important concept is **grounding skills in observed data**.
* A skill isn't merely generated from generic LLM knowledge.
* Its steps can be tied to:

  * Actual entities
  * Actual conversations
  * Actual tool calls
  * Observed execution results

This provides a connection between the skill and the evidence from which it was created.

### 16. Skill governance and "drift"

* Skills can become outdated as the underlying data, tools, or processes change.
* Because skills are represented as graphs, their dependencies can be tracked.
* If an underlying dependency changes, the system can detect that the skill may have become stale.

For example:

* A skill depends on a particular healthcare API/tool.
* Another agent discovers that the tool is broken.
* Because the skill is connected to that tool, the skill can be flagged for review.

Similarly:

* If an entity used by a skill changes, the skill can potentially be flagged as needing to be re-evaluated.

### 17. Skill versioning

* Skills have versions.
* The version represents the particular structure/content of the skill at that point in time.
* This is important for governance and tracking changes.

### 18. Review and approval process

The demonstrated workflow was roughly:

**Define scope → Traverse relevant graph → Distill skill → Review → Approve → Publish**

* A user can select a conversation or graph node as the starting point.
* The system constructs the relevant subgraph.
* An LLM annotates portions of the skill.
* The generated skill enters a review process.
* Once approved, it becomes a published skill.
* Skills can also be cryptographically signed.

### 19. Skills can depend on other skills

* The speakers mention the possibility of having **skills call other skills**.
* Large skills can potentially be broken into smaller skills.
* Those skills can then become dependencies of other skills.
* This creates a **graph of skills**.
